# 阶段 3 — 执行代码变更

**目标**：在正确的需求分支上，基于已确认的方案，实现代码变更。

**前置动作**：方案 review 已通过且用户已确认。

## 动作步骤

### 1. 检查/创建需求分支
- 查看当前分支是否为该需求的分支。
- 若不在正确分支：
  - **看几个历史分支名的取名习惯**，遵循项目现有命名风格。
  - 取一个能**正确简洁描述当前需求**的分支名（结合需求文档的 feature 名）。
- 切换/创建分支后：**执行 `codegraph sync`** 同步代码变更。

### 2. 确认 git 状态干净且与远程同步
- `git status`：工作区是否干净。
- `git fetch` + 确认与远程主分支同步（避免在过期代码上开发）。
- 同步后：**执行 `codegraph sync`**。

### 3. 执行代码实现
- 按 `technical-design.md` 的细节设计逐项实现。
- 实现过程中用 `codegraph_explore` 保持对代码逻辑的准确理解。
- 同步推进方案阶段设计好的单测与 e2e 测试（不是实现完再补）。
- **进度追踪**：实现步骤在 `ops/implementation-tracking.md` 中逐条打勾并记录 commit SHA（与代码同 commit，先 `git rev-parse HEAD` 记录基线再 commit）。
- 采用小步提交：一个逻辑单元一个 commit，commit message 遵循项目风格。

### 4. 实现中的人类协作（重要）
- **自主推进**：实现细节、命名、错误处理等按决策分层"自主推进"层处理，不打断用户。
- **发现方案未覆盖的新问题**：不擅自扩大范围——先记入 `review.md` 的待决清单（含选项+推荐+理由），继续推进可推进的部分，到阶段边界批量提交用户。
- **实现与方案冲突**：若实现中发现方案细节不合理，记入待决清单（"选项 + 推荐 + 理由"），按推荐方案继续实现，阶段边界提交用户决定；只有**阻塞后续工作的关键决策**才真正停下等。
- 技术选型/破坏性操作/涉及数据权限的改动 → 记入待决清单，批量提交，不擅自执行。

### 5. 阶段边界汇报
- 实现完成或遇到阻塞时，把**进度 + 待决点打包**汇报给用户（做了什么、测试情况、需拍板的决策清单）。
- 用户拍板后按决定修正，进入阶段 4 code review。

## 注意事项
- 未在正确分支、git 状态不干净、未与远程同步时，**不要开始写代码**。
- 分支名不符合项目命名习惯时，记入待决清单（给候选名+推荐）提交用户，或遵循现有习惯自主决定并记录。
- 不要一次实现所有内容再一次性提交——保持 commit 可追溯、可回滚。
- 阶段内不零散打扰用户；汇报在阶段边界**批量进行**。
