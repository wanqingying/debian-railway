# 阶段 4 — 自测联调与交付

**目标**：完成自测联调，交付上线，并在上线后确认无回滚触发。上线动作（提交+push+创建 MR）只在用户表达完成/上线/发布意图后执行。

**深度随改动级别调整**（见主文件）：测试范围、联调力度、是否走灰度/回滚随级别调整——L2 定向验证即可，L0 必须走完整测试与（若有核心危险变更的）灰度/回滚。

## 动作步骤

### 1. 再次同步远程主分支代码
- `git fetch` 并确认分支与远程主分支同步，必要时 rebase/merge。
- 同步后：**执行 `codegraph sync`**。

### 2. 执行单测 + e2e 测试
- 运行方案阶段设计、实现阶段写好的全部单测与 e2e 测试；L2 可只做定向测试或手工验证。
- 结果全部通过才算自测完成；失败则修复后重跑。

### 3. 联调验证
- 如有必要，要求用户执行本地调试：给出**详细的调试步骤**（引用 `technical-design.md` 的「本地与线上调试指南」）。
- 引导用户按 `technical-design.md` 的「上线 checklist」与「灰度与回滚方案」核对上线前置条件（环境变量、数据库、第三方平台操作、回滚步骤）。

### 4. 交付（受控动作）
**没有用户明确指令，禁止 push 代码。**
- 用户表达"完成开发、上线、发布"等意图后：
  1. 再次同步远程主分支代码（`git fetch` + 确认同步）。
  2. 提交所有变更（含文档：需求、方案、review、进度追踪——与代码同 commit 链）。
  3. `git push` 需求分支。
  4. **创建 MR**：提供 MR 描述（需求摘要、改动概览、测试结果、上线 checklist 状态、review 结论链接、级别与是否需要灰度/回滚）。

### 5. 上线后观察与回滚（按需）
- 若方案含「灰度与回滚方案」：按计划放量，观察预设指标；命中**停止/回滚触发条件**时，立即执行方案中的回滚步骤与补救措施，并通知用户。
- 观察期内保持值守直到放量完成或回滚；结果（含异常）记入 `review.md`。
- 无灰度/回滚的普通改动（如 L2）可跳过本节。

## 注意事项
- push/MR 是受控动作，未获明确指令不得执行。
- 文档与代码一起交付，保证可追溯（review.md 记录、进度追踪、checklist 状态）。
- MR 描述要自包含：审查者不看会话也能理解改动。
- **灰度/回滚只对"核心危险变更"执行**（见阶段 1 B10）；普通 bug 修复、布局调整等无需走此流程。
