# 阶段 4 — 自测联调与交付

**目标**：完成自测联调，交付一个处于可 review 状态的 PR，并在上线后确认无回滚触发。提交、push、PR 与合并遵循项目自身的 git 规范；合并需等待用户明确 LGTM。

**深度随改动级别调整**（见主文件）：测试范围、联调力度、是否走灰度/回滚随级别调整——L2 定向验证即可，L0 必须走完整测试与（若有核心危险变更的）灰度/回滚。

## 动作步骤

### 1. 再次同步远程主分支代码
- `git fetch` 并确认分支与远程主分支同步，必要时 rebase/merge。

### 2. 执行单测 + e2e 测试
- 运行方案阶段设计、实现阶段写好的全部单测与 e2e 测试；L2 可只做定向测试或手工验证。
- 结果全部通过才算自测完成；失败则修复后重跑。

### 3. 联调验证
- 如有必要，要求用户执行本地调试：给出**详细的调试步骤**（有 `design.md` 时取自其「本地与线上调试指南」）。
- 与用户核对上线前置条件（环境变量、数据库、第三方平台操作、回滚步骤）——有 `design.md` 时取自其「上线 checklist」与「灰度与回滚方案」。

### 4. 交付
当实现完成、可用的检查全部通过、且你自己的 review 认为就绪后：
  1. 再次同步远程主分支代码（`git fetch` + 确认同步）。
  2. 只格式化本分支改动的文件，使用项目的格式化工具；绝不做全仓库重排。
  3. 提交变更（若本次有迭代文档，与代码同 commit 链）。
  4. `git push` 需求分支。
  5. **打开处于可 review 状态的 PR。** 其描述即记录（主文件 →「文档」），其中写明级别与是否需要灰度/回滚；有迭代时，摘要并链接之。描述必须自包含：审查者不看会话也能理解改动。
  6. 仅在用户明确 LGTM 后合并。

### 5. 上线后观察与回滚（按需）
- 若方案含「灰度与回滚方案」：按计划放量，观察预设指标；命中**停止/回滚触发条件**时，立即执行方案中的回滚步骤与补救措施，并通知用户。
- 观察期内保持值守直到放量完成或回滚；记录结果（含异常）并汇报用户。
- 无灰度/回滚的普通改动（如 L2）可跳过本节。

## 注意事项
- **灰度/回滚只对"核心危险变更"执行**（见阶段 1 B10）；普通 bug 修复、布局调整等无需走此流程。
