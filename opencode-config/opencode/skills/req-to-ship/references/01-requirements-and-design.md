# 阶段 1 — 需求澄清与技术方案设计

**目标**：先把用户的需求细化到**无歧义、可落地**，再据此定下**架构合理、细节完整、可落地**的技术方案。

**仅当本次工作有迭代时才落文件**（主文件 →「文档」）：下面的 `design.md` 模板——需求与技术方案合为一篇——只适用于获得迭代的工作。否则按级别所需的深度做同样的思考，把决策在对话中交给人类，并把结论带进 PR 描述。

**前置动作**：确保工作区已建索引（`codegraph status`；没有则 `codegraph init --yes`），再用 `codegraph_explore` 在现有系统中定位，并对照源码核实它的发现（SKILL.md →「工具操作速查」）。需求子部分（Part A）是方案（Part B）的前置输入，**需求没写清楚不进入设计**。

---

## Part A — 需求澄清（`design.md` 的需求部分）

### A1. 理解需求
- 完整读取用户的需求说明，不遗漏细节；**保留用户原始表述**作为文档附录，避免信息丢失。
- 明确需求的**背景（为什么做）**、**目标（解决什么问题/业务价值）**、**范围（做什么/不做什么）**、**参与者（谁用、谁触发）**。
- 若是对已有 feature 的变更/迭代：先读该 feature 的 README 与其最近一次迭代，确认基线与既有设计；仅当本次工作有迭代时才新开迭代目录。

### A2. 确定改动级别（优先，决定流程深度）
- **先定级别**：按主文件「改动级别与流程深度」的判定问题做**初判**。级别决定本阶段及后续所有阶段的流程深度——先定级别，再据此决定各项要做多深。
- 需求看着小并不代表改动小：初判后要在 B1/B6 梳理完代码与影响面后**确认或修正**，以修正后的级别为准。
- 级别与理由记录到 `design.md` 或 PR 描述（如「改动级别：L1（理由…）」）。级别存疑时按**更高一级**处理。

### A3. 结合现有代码理解
（本步只需理解到"能界定需求与影响范围"；结构与插入点的深入梳理留到 B1，避免重复劳动。）
- **先找项目既有知识**（SKILL.md →「工具操作速查」→ *查找项目既有知识*）：docs 索引（项目若维护）定位区域，feature 的 `README.md` 与其最近一次迭代给出基线，`rg` 搜索语料，`qmd`（仅当已安装，否则说明后跳过）做自然语言问答。重新推导一个已记录的决策是最常见的浪费。
- 用 `codegraph_explore` 找出需求涉及的相关模块、调用链、数据模型、已有实现，再用 `rg` 确认这一集合——explore 返回的是起点，不是全部写入方和调用方。
- 判断这是**新功能**、**修改现有行为**还是**修复**，会影响哪些现有功能。
- 需求引用了现有 UI/流程/接口时，先读对应代码确认现状。

### A4. 细化与澄清
- 把模糊点列出，**先自主处理能处理的**：
  - 能从现有代码/文档推断的：自己查证，直接确定，不必再问。
  - 边界条件（空数据、异常、并发）、非功能性要求、交互细节、依赖关系：先基于现有系统合理推断，标记为"待确认"。
- 涉及**范围、优先级、产品行为**的决策 → 按主文件决策分层**必须问人**：记入待决清单，阶段边界批量呈现。
- 实现细节类的歧义（如何实现等）→ 留到 Part B（技术方案）处理；相关待决/自主决策记录下来。
- 分析合理性：需求是否与现有架构冲突？是否超出合理范围？有问题记为待决点连同理由提交。

### A5. 产出需求部分

**仅当本次工作有迭代时。** 写入迭代目录下 `design.md` 的需求部分（**位置与命名以主文件「文档」为准**）。内容结构模板：

```markdown
# <Feature> 需求文档

## 变更级别
（L0/L1/L2 + 一句话理由；级别按主文件「改动级别与流程深度」判定）

## 1. 背景与目标
### 背景（为什么做、要解决的痛点）
### 目标（解决什么问题、期望的业务价值）
### 衡量标准（怎么判断目标达成，尽量可量化）
### 需求来源与参考资料
（原始需求单 / 产品文档 / 设计稿 / 原型的引用：链接或仓库路径。
 产品侧产出的内容保留其原始出处，不要复制全文——引用即可，方便回溯原始意图。）

## 2. 需求描述
### 功能列表
（每个功能：描述、优先级、验收标准）
### 用户流程与交互
（从用户视角：入口 → 操作 → 结果，含正常/异常路径）
### UI 与交互要求
（界面、交互、状态反馈、文案；若有设计稿/原型，引用其原始文档与具体页面）

## 3. 非功能性要求
（性能、安全、兼容性、可维护性）

## 4. 边界与约束
（不做什么、依赖项、限制）

## 5. 验收标准
（可验证清单：满足这些即算完成）
```

> **背景与目标是全文的驱动因素**——它是需求背后的底层动因，后续所有分析、架构设计与取舍都必须围绕它展开，因此放在最前面；方案 review（B11）时核对目标对齐：若某设计无法服务于该目标，要么重新设计，要么明确指出并说明原因。
>
> **需求文档聚焦"要什么"，不写技术实现**。数据/接口影响这类偏技术的内容归入技术方案文档（B6），需求文档只描述业务与用户视角。

## Part B — 技术方案设计（同一份 `design.md` 的方案部分）

### B1. 现有代码与架构梳理
- 用 `codegraph_explore` 梳理涉及的模块、服务边界、数据流与现有相似实现——先用问题定位，再用文件与符号名钉住流程——并在写入方案前用 `rg` 确认写入方/调用方。
- 确认**改动的插入点**：在哪个层/模块实现、需要改哪些文件、会触及哪些既有逻辑。
- **附关键代码/文件引用**：给出相关文件路径 + 行号（如 `path/to/file.ts:123`）或关键符号名，并说明"为什么相关、后续要改什么"。**只给定位信息，不粘贴大段源码**——目标是让实现阶段能快速定位模块与改动点，而不是复述现有代码。
- **在此确认/修正改动级别**（见 A2）：实际改动范围与影响面可能高于需求初判。

### B2. 关键技术调研（按需）
仅当**引入新的底层/核心依赖包**时必做；无新依赖写"N/A 无新依赖"并注明理由。
- 查**官方文档** + **网上搜索**，调研：用法、是否满足需求、版本/稳定性。
- **是否最优选择**：与其他候选方案对比（功能覆盖、维护活跃度、性能、社区成熟度、许可证），给出选型理由。

### B3. 架构设计（必须）
- 输出整体架构：模块划分、层与边界、数据流、对外接口、与现有系统的关系。
- 初步设计后，**对整体和关键设计进行反思评估**：是否存在其他设计？有哪些候选方案？逐一对比（复杂度、可维护性、性能、扩展性、风险），得出**适合本项目当前情况的最优解**并说明理由。
- 涉及架构分歧时，把对比结论作为架构设计的一部分记录（有迭代时写入 `design.md`，否则写入 PR 描述）。

### B4. 数据库与表设计（可选，有则必做）
- 说明数据库改动：新增/修改的表、字段、索引、约束。
- **附带迁移说明**：迁移脚本/方式、数据兼容处理、回滚方案。

### B5. 各部分细节设计（必须）
- 对每个功能点/模块给出实现级细节：关键类/函数、接口签名、状态流转、异常处理、边界条件。
- 关键算法/复杂逻辑给出伪代码或流程说明。

### B6. 数据与接口影响
- 涉及的数据结构与字段变化、对外接口契约、与现有系统的关系、受影响的消费方。

### B7. 测试设计（必须）
- 设计**覆盖核心流程**的单测用例清单（正常路径 + 关键异常路径）。
- 设计 e2e 用例清单：走通端到端用户流程。
- 与需求的验收标准逐条对应，保证每个验收点都有测试覆盖。
- **深度随级别调整**：L0 覆盖核心流程 + 关键异常 + e2e；L1 覆盖核心路径；L2 定向测试或手工验证即可。

### B8. 本地与线上调试指南（必须）
- **面向用户的联调指南**：如何本地启动、如何连线上、如何触发该需求涉及的流程、常见问题定位手段。
- 面向用户的部分可同步到 `user-guide.md`。

### B9. 上线 checklist（必须）
- 环境变量/配置（新增 env、是否写入 Railway Variables）。
- 数据库迁移执行时机。
- 第三方平台操作（是否需要申请/配置/审批）。
- 监控项、需要通知的团队。

### B10. 灰度与回滚方案（按需）
读完改动范围与影响面（B1/B6）后，判断本次改动**是否存在核心危险变更**。命中以下任一项才需要写本节；否则写"N/A 无核心危险变更"并给一句理由即可：
- 数据库 schema / 数据迁移
- 核心 agent / 核心引擎 / 核心业务逻辑变更
- 底层框架或核心依赖升级
- 涉及费用、权限、数据完整性
- 难以回滚的改动

**不需要的典型**：修复 bug、页面布局调整、文案、普通小功能。级别对应：**L0 必做，L1 按需，L2 通常不做**。

需要时，本节必须独立成项、可执行，不能只写"有问题就回滚"：
- **灰度**：是否需要灰度、灰度范围/比例/时长、放量节奏、观察指标与停止条件。
- **回滚**：明确**触发条件**与**可执行的回滚操作步骤**（逐步、可直接照做）。
- **补救措施**：回滚后如何修复/补救已产生的数据或状态（补偿、清理、回填）。
- **必要时给出操作脚本**（回滚/补偿脚本），并说明脚本的执行前置条件与验证方式。

### B11. 方案 review
- 初步生成方案后，**重新查看方案涉及到的模块和代码**，确认：
  - 目标对齐：对照需求的背景与目标核对本方案是否服务于目标；偏离目标的设计要么调整，要么显式说明原因。
  - 方案合理性：设计是否匹配现有架构、无过度设计。
  - 可落地性：改动范围可控、无隐藏依赖、关键细节无遗漏。
- 有迭代时，把 review 结论（已确认/已否决的设计点 + 理由）作为「方案 review」章节写入 `design.md`，**不另立文档**；没有迭代时，把 reviewer 需要看到的方案决策连同理由写入 PR 描述。

> **产出统一**：有迭代时，方案阶段的全部产出（B1 代码梳理、B3 架构、B5 细节、B6 数据接口、B7 测试设计、B8 调试指南、B9 上线 checklist、B10 灰度/回滚、B11 方案 review）**都写进这一份 `design.md`**——一份文档，不再拆分独立文件；没有迭代时，方案取舍、测试结果、以及任何发布/回滚步骤写入 PR 描述。**L2 的技术方案可省略**（改动自明、无设计取舍时）。

## Part C — 阶段边界：批量拍板

- 把 Part A 与 Part B 的**全部待决点合并成一份清单**，按决策点编号呈现：**问题背景 + 候选选项 + 推荐项 + 理由**，让人做选择题。
- 一次集中呈现，标注哪些是**阻塞项**（必须先定，如范围未定）、哪些可**后置**（不阻塞继续）。
- **高风险护栏**：若需求范围高度不确定、或需求很大，把"范围"当作**关键阻塞点提前停下确认**，再投入方案设计——避免在模糊需求上做完大量设计后返工。需求清晰时默认一路做到本边界。
- 问题带上下文、具体明确，不让人猜你在问什么。
- 用户一次性拍板后，把决定记录下来（有迭代时写回 `design.md` 与迭代记录）；修正其余待决点后进入阶段 2。
- **L2 可弱化本环节**：改动无害且决策权明了时，可给用户一句话说明后直接进入实现，不必强行凑出待决清单。

## 注意事项
- **先定改动级别**：级别决定投入多少（测试深度、review 力度、是否需要灰度回滚、人类确认点多少）。不要给无害的小改动套重流程，也不要在核心改动上偷工。
- 需求是方案设计的输入，**没写清楚不要开始设计**。
- **背景与目标是驱动因素**，方案应围绕它、不偏离；方案 review 时逐条核对即可。
- **需求只写业务/用户视角**，数据与接口影响归到方案文档（B6）。
- 关键代码/文件引用要**可定位**（路径 + 行号/符号），不要贴大段源码。
- 有迭代时，需求与方案集中在 `design.md` 一份文档内，不再拆分独立文件，便于实现阶段一处查阅。
- 验收标准要**可验证**（"用户能 X"而非"系统应该 X 比较好"）。
- 在 `design.md` 中，关键技术调研和架构对比是**必填项**（无新依赖/无架构分歧时明确写"N/A"并说明），不能整节省略。PR 描述仅在确实做过选择时才提及它们。
- 单测/e2e 设计在方案阶段完成，实现时照着执行，不是实现完再补。
- 方案阶段不写生产代码，但**允许做技术验证（spike）**：对不确定的选型可写临时验证代码确认可行性，结果记录下来，验证代码不并入交付。
- **不要边聊边澄清**：先把能查证、能推断的都做完，产生完整草案，剩余问题一次性问清，避免零散打扰用户。
