# 阶段 3 — 执行 code review

**目标**：对实现进行系统化审查，覆盖需求符合与功能正确性、技术/架构合理性、对现有功能的影响三个维度。审查通过前不算完成。

**核心循环**：若 review 发现实现未完成或有问题 → 回到阶段 2 继续修改，直到通过。若问题**源于需求或方案本身**（而非实现），**允许回退**到阶段 1 修正，再继续——回退是正常节奏，不当作失败。

**深度随改动级别调整**（见主文件）：L0 三维审查全做、可并行子 agent；L1 标准三维；L2 轻量审查即可，不必强行铺满三维。

## 动作步骤

### 1. 评估实现步骤是否完成
- 对照已确认的方案（有迭代时为 `design.md`；commit 记录即步骤记录）：
  - 是否所有设计项都已实现？
  - 设计好的单测/e2e 是否都已写并通过？
- 若未完成：回到阶段 2，说明缺口。
- L2 可跳过逐项对照，直接看改动是否达成需求目标。

### 2. 确认 commit 记录完整
- `git log <base>..HEAD`：每个逻辑步骤都有自己的提交；不存在追踪文件。

### 3. 阅读需求 + 技术方案
- 重读需求与已确认的方案（存在时为 `design.md`），以它们为审查基准，不凭印象评。

### 4. 用 git 查看代码变更
- `git diff` / `git log` 查看本次分支相对基准分支的完整变更。
- **逐行读改动。** 不要扫一眼人写的函数就假定函数体没问题。若一处改动难以跟上，这本身就是一条发现——后来的读者（以及下一个编辑它的 agent）同样会吃力；与其批准看不懂的代码，不如要求澄清或简化。

### 5. 三维审查（可并行用子 agent，需自行判断）
三个维度独立评估，可并行委派子 agent 各自审查后汇总。**审查深度随级别调整**：L0/L1 逐项做全，L2 抓主要风险点即可，不必强行铺满。

**a. 需求符合性与功能正确性**
- **实现了需求**：对照 `design.md` / 需求，要求的东西是否都在且正确？列出缺失或只做了一半的部分。
- **无范围蔓延**：是否有未被要求却新增的东西（未要求的开关、行为或抽象）？额外范围是要暴露的发现，不是加分项——留不留由人类决定。
- 系统角度：功能实现是否合理、是否存在逻辑漏洞、是否选择了最佳实现路径。
- 用户角度：使用流程是否完整、使用体验是否最佳、用户操作反馈与提示是否正确合理。
- **测试也是代码——像审查生产代码一样审查它们**：
  - 每个测试断言的是真实行为，还是同义反复 / 对代码当前输出的快照？
  - **代码坏了它会失败吗？** 因错误原因通过的测试比没有更糟——说出一个能让它变红的改动。
  - 过度 mock 是否让它在真实逻辑出错时仍通过？错误与边界情况是否覆盖，而不只是 happy path？
  - 测试全绿本身不是证据：对行为/输出/费用有变化的改动，坚持要有能证明该改动的验证。

**b. 技术与架构合理性**
- 审查架构设计是否合理、技术细节与代码坏味道。
- 从架构、规范、坏味道、可维护性、安全、性能多个角度评估。
- **命名与注释**：名字是否揭示了它是什么或做什么（好名字无需注释）？注释是否解释*为什么*——一个决策、一个约束——而不是复述*什么*？标记只是复述代码的注释，以及只有靠注释才看得懂的代码。
- **坏味道基线**（启发式标签，绝不是硬性违规；仓库有明确规范以规范为准；工具已强制的跳过）：神秘命名、重复代码、依恋情结、数据泥团、基本类型偏执、重复的 switch、散弹式修改、发散式变化、夸夸其谈通用性、过长的消息链、中间人、被拒绝的遗赠（Fowler《重构》第 3 章）。说出味道的名字——"疑似依恋情结"——而不是笼统地说代码"有味道"。
- **架构与新引入的核心依赖/复杂库**：查官方文档、网上搜索、最佳实践，对比反思可能的其他方案，评估选型是否最优。

**b'. 代码健壮性**（b 的专项子项，逐条核对，不凭印象放过）
- **异常处理**：异常路径是否都被处理？是否会向上抛出难以理解的错误或导致崩溃？是否存在吞掉异常掩盖问题的情况？失败时是否优雅降级而非中断整条流程？
- **边界与非法输入**：空值、零值、超长、超限、格式非法、恶意输入是否都有明确处理路径？外部输入（用户、接口、配置）是否经过校验？
- **部分失败与一致性**：多步骤操作在中间步骤失败时如何收尾？是否产生脏数据、半成品或状态不一致？是否需要事务/补偿/重试/幂等？
- **资源管理**：连接、文件句柄、临时文件、定时器等是否在失败路径也正确释放？有无泄漏或资源耗尽风险？
- **并发与竞态**：共享状态、异步回调、并发访问是否存在竞态条件或数据竞争？写入是否需要加锁/原子操作？
- **超时与取消**：对依赖外部系统/网络的调用是否有超时和失败重试策略？任务被取消/中断时是否清理干净？
- **可观测性** —— 逐条核对，不凭印象：
  - **关键步骤有可 grep 的日志**：新流程的入口与出口、每个重要的分支/决策、以及每次外部调用（provider、DB 写入、队列、webhook）都打一条日志，说明发生了什么、带哪些标识符。无法靠日志跟下来的运行，在生产中就是不可审查的——把信号与功能一起发布，而不是等第一次事故后补。
  - **结构化、带关联标识**：包含能把一行日志关联到一次运行的信息——请求/运行 id、租户/工作区 id、工作单元、provider id——而不是干巴巴的"出错了"。
  - **用仓库既有的可观测性通道，不自造**：把 trace 与有产品意义的事件走仓库已有的机制，**不要新增自制的遥测/运行表**。
  - **错误带上下文且不隐藏**：失败要带可行动的上下文记录；不要吞异常或静默 log-and-continue（见上面的异常处理项）。
  - **日志不含密钥或 PII**：绝不输出 token、密钥、凭据或原始个人数据。
  - **信号而非噪音**：密集循环内不要逐条打日志；合理使用级别（info 记录里程碑，warn/error 给需要有人处理的事）。
  - **仅凭日志可定位**：只给日志，运维能否判断新行为是否执行了、失败的话为什么？

**c. 对现有功能的影响**
- 本次改动是否破坏了其他功能？进行完整影响面评估（调用的模块、被调用的模块、数据格式变更的消费方、配置/环境依赖）。

### 6. 记录 review 结果
- 有迭代时，向当前迭代的记录（`README.md`）追加 code review 段落：
  - 每个维度的问题列表，每条含**位置 + 严重程度 + 建议修复方式**；统一用一套词汇：**blocker**（合并前必须修复——正确性、安全、数据、破坏的契约）、**should-fix**（真实存在，但不阻塞合并）、**nit**（偏好；前缀 `Nit:`，绝不因其阻塞）。
  - 通过/不通过的结论。
  - 实现中已做但方案未覆盖的自主决策及其理由（人机协作机制"自主推进"层的追溯）。
- 没有迭代时，修复发现，并只把 reviewer 需要的内容带进 PR 描述：那些带理由的自主决策，以及任何遗留风险或未修复的发现。
- 若发现问题：回到阶段 2 修复，修复后再 review；问题源于需求/方案本身则回退阶段 1。
- **人类批量签收**：涉及 UX/产品行为变化、或 review 有争议结论时，把签收点 + 变更摘要打包呈现用户，一次确认后再视为 review 通过；L0/L1 尤其不能省，L2 可自行确认。

## 注意事项
- review 以需求+方案为基准，独立评估，不自我美化。
- 影响面评估（维度 c）最容易遗漏，务必检查数据格式/接口变更的所有消费方。
- 子 agent 并行审查时，给每个 agent 明确的目标和输出格式，最后统一汇总。
- 审查发现的**新需求点**（超出当前需求范围的合理想法）不要并入实现，记为遗留事项，留待用户决定。
