# 阶段 2 — 技术方案设计与 review

**目标**：基于已确认的需求文档，结合现有代码逻辑和整体架构，产出一份**架构合理、包含关键细节、可落地**的技术方案文档，并经过方案 review 确认。

**前置动作**：重读当前迭代的 `requirements.md`；用 `codegraph_explore` 查看方案涉及模块的调用链与实现；必要时 `codegraph sync` 保持索引新鲜。

## 动作步骤

### 1. 理解现有架构与代码
- 用 `codegraph_explore` 系统梳理：涉及的模块、服务边界、数据流、现有相似实现。
- 确认改动的插入点：在哪个层/模块实现、需要改哪些文件、会触及哪些既有逻辑。

### 2. 关键技术调研（可选，按需）
仅当**引入新的底层/核心依赖包**时必做；无新依赖写"N/A 无新依赖"并注明理由。
- 查**官方文档** + **网上搜索**，调研：用法、是否满足需求、版本/稳定性。
- **是否最优选择**：与其他候选方案进行对比评估（功能覆盖、维护活跃度、性能、社区成熟度、许可证），给出选型理由。

### 3. 架构设计（必须）
- 输出整体架构设计：模块划分、层与边界、数据流、对外接口、与现有系统的关系。
- 初步设计后，**对整体和关键设计进行反思评估**：
  - 是否存在其他设计？有哪些候选方案？
  - 逐一对比评估（复杂度、可维护性、性能、扩展性、风险），得出**适合本项目当前情况的最优解**并说明理由。
- 涉及架构分歧时，把对比结论记录到 `review.md`。

### 4. 数据库与表设计（可选，有则必做）
- 说明数据库改动：新增/修改的表、字段、索引、约束。
- **附带迁移说明**：迁移脚本/方式、数据兼容处理、回滚方案。

### 5. 各部分细节设计（必须）
- 对每个功能点/模块给出实现级细节：关键类/函数、接口签名、状态流转、异常处理、边界条件。
- 关键算法/复杂逻辑给出伪代码或流程说明。

### 6. 核心流程单测与 e2e 测试设计（必须）
- 设计**覆盖核心流程**的单测用例清单（正常路径 + 关键异常路径）。
- 设计 e2e 用例清单：走通端到端用户流程。
- 与需求文档的验收标准对应，保证每个验收点有测试覆盖。

### 7. 本地与线上调试指南（必须）
- 产出 `ops/debug-guides.md`：**面向用户的联调指南**——如何本地启动、如何连线上、如何触发该需求涉及的流程、常见问题定位手段。

### 8. 上线 checklist（必须）
- 产出 `ops/launch-checklist.md`：上线前需准备的所有事项——
  - 环境变量/配置（新增 env、是否写入 Railway Variables）
  - 数据库迁移执行时机
  - 第三方平台操作（是否需要申请/配置/审批）
  - 灰度/回滚方案、数据清理或回填、监控项、需要通知的团队

### 9. 方案 review
- 初步生成方案后，**重新查看方案涉及到的模块和代码**，确认：
  - 方案合理性：设计是否匹配现有架构、无过度设计。
  - 可落地性：改动范围可控、无隐藏依赖、关键细节无遗漏。
  - 步骤 3 的架构对比结论是否站得住。
- 把 review 结论写入当前迭代的 `review.md`（结论 + 已确认/已否决的设计点 + 理由）。

### 10. 选型批量拍板
- 阶段边界时，把**全部选型/架构决策打包**呈现：每个为"候选方案 + 推荐 + 理由 + 对比结论"。
- 用户一次性拍板，agent 根据决定更新 `technical-design.md` 并记录到 `review.md`。
- 用户确认后进入阶段 3。若用户对某些选型有异议，更新方案后再次确认（仅针对有异议项，不重复全部）。

## 注意事项
- **文档位置以主文件「文档目录结构规范」为准**：方案→`technical-design.md`，review→`review.md`，checklist→`ops/launch-checklist.md`，调试指南→`ops/debug-guides.md`。
- 关键技术调研和架构对比是**必填项**（无新依赖/无架构分歧时明确写"N/A"并说明），不能整节省略。
- e2e/单测设计在方案阶段完成，实现时照着执行，不是实现完再补。
- 方案阶段不写代码，但**允许做技术验证（spike）**：对不确定的选型，可写临时验证代码确认可行性，验证结果记入 `review.md`，验证代码不并入交付。
