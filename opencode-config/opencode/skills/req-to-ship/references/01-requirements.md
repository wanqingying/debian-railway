# 阶段 1 — 需求澄清与初始化

**目标**：把用户的需求说明，结合现有系统的设计和代码逻辑，细化为一份**详细、可落地、无歧义**的需求文档。

**前置动作**：先执行 `codegraph sync` 同步代码变更，再用 `codegraph_explore` 分析现有系统。

## 动作步骤

### 1. 理解需求
- 完整读取用户的需求说明，不遗漏细节。
- 列出需求的**目标**（要解决什么问题）、**范围**（做什么/不做什么）、**参与者**（谁用、谁来触发）。

### 2. 结合现有代码理解
- 用 `codegraph_explore` 找出需求涉及的相关模块、调用链、数据模型、已有实现。
- 搞清楚：这个需求是**新功能**、**修改现有行为**、还是**修复**？会影响哪些现有功能？
- 若需求引用了现有 UI/流程/接口，先读对应代码确认现状。

### 3. 细化与澄清
- 把模糊点列出，**先自主处理能处理的**：
  - 能从现有代码/文档推断的：自己查证，直接写入需求文档。
  - 边界条件（空数据、异常、并发）、非功能性要求（性能、安全、兼容性）、交互细节、依赖关系——先基于现有系统合理推断，标记为"待确认"。
- 涉及**范围、优先级、产品行为**的决策 → 按主文件决策分层**必须问人**：记入待决清单，阶段边界批量呈现"选项 + 推荐 + 理由"。
- 实现细节类的歧义（如何实现等）→ 不在本阶段纠缠，记入 `review.md` 待方案阶段处理。
- 分析合理性：需求是否与现有架构冲突？是否超出合理范围？如有问题记录为待决点，连同理由提交用户。

### 4. 产出需求文档

写入主文件规定的迭代目录下 `requirements.md`（**文档位置与命名以主文件「文档目录结构规范」为准**，不在此重复定义目录）。内容结构模板：

```markdown
# <Feature> 需求文档

## 背景与目标
（为什么做、解决什么问题、衡量标准）

## 需求描述
### 功能列表
（每个功能：描述、优先级、验收标准）

### 用户流程
（从用户角度：入口 → 操作 → 结果，含正常/异常路径）

## 非功能性要求
（性能、安全、兼容性、可维护性）

## 边界与约束
（不做什么、依赖项、限制）

## 数据与接口影响
（涉及的数据、对外接口、与现有系统的关系）

## 验收标准
（可验证的清单：满足这些就算完成）
```

### 5. 批量呈现待决点，一次确认
- 阶段边界时，把**全部待决点打包**呈现给用户（每个：问题背景 + 选项 + 推荐 + 理由，标注阻塞/可后置）。
- 向用户汇报需求文档要点，用户一次性拍板。
- 用户拍板后，将决定写回 `requirements.md`（修正"待确认"项）并记录到 `review.md`。
- 若用户的决定改变范围/优先级 → 更新需求文档后进入阶段 2；否则直接进入。

## 注意事项
- 需求文档是阶段 2 的输入，**没写清楚不要开始设计**。
- 验收标准要**可验证**（"用户能 X"而非"系统应该 X 比较好"）。
- 用户用口语描述需求时，把它转成结构化文档，但保留用户原始表述作为附录，避免信息丢失。
- **不要边聊边澄清**：agent 先把能查证、能推断的都做完，产生完整草案，把剩余问题一次性问清，避免零散打扰用户。
