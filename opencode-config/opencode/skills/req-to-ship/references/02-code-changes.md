# 阶段 2 — 执行代码变更

**目标**：在正确的需求分支上，基于已确认的方案，实现代码变更。

**前置动作**：阶段 1 的方案 review 已通过、用户已确认待决点（**L2 可豁免**：改动自明、无设计取舍时直接进入实现）。

**深度随改动级别调整**（见主文件）：L0 严格小步提交（commit 记录即步骤追踪）；L1 标准；L2 可单次提交。

## 动作步骤

### 1. 检查/创建需求分支
- 查看当前分支是否为该需求的分支。
- 若不在正确分支：
  - **看几个历史分支名的取名习惯**，遵循项目现有命名风格。
  - 取一个能**正确简洁描述当前需求**的分支名（结合需求的 feature 名）。
- 新 worktree 没有索引：先在那里执行一次 `codegraph init --yes`（之后由文件监听器保持新鲜）。
- L2 也要有自己的分支：每个改动都走特性分支 + PR（按项目 git 规范）。

### 2. 确认 git 状态干净且与远程同步
- `git status`：工作区是否干净。
- `git fetch` + 确认与远程主分支同步（避免在过期代码上开发）。

### 3. 执行代码实现
- 按已确认的方案逐项实现（有迭代时为 `design.md`；L2 无方案时按需求本身实现）。
- 实现过程中用 `codegraph_explore` 保持对正在改动的代码的准确认识——点名你将要编辑的符号，让源码与调用方一起返回——并在修改前先读该文件。
- 同步推进方案阶段设计好的单测与 e2e 测试（不是实现完再补）。
- **进度追踪即 commit 记录**：每个逻辑步骤一次提交、配语义化信息（按项目 git 规范），让 `git log` 显示顺序、`git blame` 显示来源；不存在追踪文件。迭代记录只在需要时引用一次提交区间。
- 采用小步提交：一个逻辑单元一个 commit，commit message 遵循项目风格（L2 可单次提交）。

### 4. 实现中的人类协作（重要）
- **自主推进**：实现细节、命名、错误处理等按决策分层"自主推进"层处理，不打断用户。
- **发现方案未覆盖的新问题**：不擅自扩大范围——先加入待决清单（含选项+推荐+理由），继续推进可推进的部分，到阶段边界批量提交用户。
- **实现与方案冲突**：若实现中发现方案细节不合理，记入待决清单（"选项 + 推荐 + 理由"），按推荐方案继续实现，阶段边界提交用户决定；只有**阻塞后续工作的关键决策**才真正停下等。
- 技术选型/破坏性操作/涉及数据权限的改动 → 记入待决清单，批量提交，不擅自执行。

### 5. 阶段边界汇报
- 实现完成或遇到阻塞时，把**进度 + 待决点打包**汇报给用户（做了什么、测试情况、需拍板的决策清单）；L2 可一句话带过。
- 用户拍板后按决定修正，进入阶段 3 code review。

## 注意事项
- 未在正确分支、git 状态不干净、未与远程同步时，**不要开始写代码**。
- 分支名不符合项目命名习惯时，记入待决清单（给候选名+推荐）提交用户，或遵循现有习惯自主决定并记录。
- 不要一次实现所有内容再一次性提交——保持 commit 可追溯、可回滚。
- 阶段内不零散打扰用户；汇报在阶段边界**批量进行**。
