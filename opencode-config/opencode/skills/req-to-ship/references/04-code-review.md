# 阶段 4 — 执行 code review

**目标**：对实现进行系统化审查，覆盖功能正确性、技术/架构合理性、对现有功能的影响三个维度。审查通过前不算完成。

**核心循环**：若 review 发现实现未完成或有问题 → 回到阶段 3 继续修改，直到通过。若问题**源于需求或方案本身**（而非实现），**允许回退**到阶段 1（需求）或 2（方案）修正，再继续——回退是正常节奏，不当作失败。

## 动作步骤

### 1. 评估实现步骤是否完成
- 对照 `technical-design.md` 的细节设计与 `ops/implementation-tracking.md` 的进度追踪：
  - 是否所有设计项都已实现？
  - 设计好的单测/e2e 是否都已写并通过？
- 若未完成：回到阶段 3，说明缺口。

### 2. 已完成 → 更新进度追踪文档
- 在 `ops/implementation-tracking.md` 中确认所有步骤已完成并记录对应 commit SHA。

### 3. 阅读需求 + 技术方案
- 重读 `requirements.md` 与 `technical-design.md`，以它们为审查基准，不凭印象评。

### 4. 用 git 查看代码变更
- `git diff` / `git log` 查看本次分支相对基准分支的完整变更。

### 5. 三维审查（可并行用子 agent，需自行判断）
三个维度独立评估，可并行委派子 agent 各自审查后汇总：

**a. 功能正确性与合理性**
- 系统角度：功能实现是否合理、是否存在逻辑漏洞、是否选择了最佳实现路径。
- 用户角度：使用流程是否完整、使用体验是否最佳、用户操作反馈与提示是否正确合理。

**b. 技术与架构合理性**
- 审查架构设计是否合理、技术细节与代码坏味道。
- 从架构、规范、坏味道、可维护性、安全、性能多个角度评估。
- **架构与新引入的核心依赖/复杂库**：查官方文档、网上搜索、最佳实践，对比反思可能的其他方案，评估选型是否最优。

**b'. 代码健壮性**（b 的专项子项，逐条核对，不凭印象放过）
- **异常处理**：异常路径是否都被处理？是否会向上抛出难以理解的错误或导致崩溃？是否存在吞掉异常掩盖问题的情况？失败时是否优雅降级而非中断整条流程？
- **边界与非法输入**：空值、零值、超长、超限、格式非法、恶意输入是否都有明确处理路径？外部输入（用户、接口、配置）是否经过校验？
- **部分失败与一致性**：多步骤操作在中间步骤失败时如何收尾？是否产生脏数据、半成品或状态不一致？是否需要事务/补偿/重试/幂等？
- **资源管理**：连接、文件句柄、临时文件、定时器等是否在失败路径也正确释放？有无泄漏或资源耗尽风险？
- **并发与竞态**：共享状态、异步回调、并发访问是否存在竞态条件或数据竞争？写入是否需要加锁/原子操作？
- **超时与取消**：对依赖外部系统/网络的调用是否有超时和失败重试策略？任务被取消/中断时是否清理干净？
- **可诊断性**：关键路径是否有可用的日志/指标，出错时能否快速定位（而不只是"报了个错"）？错误信息是否对用户/运维有实际指导意义？

**c. 对现有功能的影响**
- 本次改动是否破坏了其他功能？进行完整影响面评估（调用的模块、被调用的模块、数据格式变更的消费方、配置/环境依赖）。

### 6. 记录 review 结果
- 结论写入当前迭代的 `review.md`（追加 code review 段落）：
  - 每个维度的问题列表（严重程度、涉及位置、建议修复方式）
  - 通过/不通过的结论
  - 实现中已做但方案未覆盖的自主决策及其理由（人机协作机制"自主推进"层的追溯）
- 若发现问题：回到阶段 3 修复，修复后再 review；问题源于需求/方案本身则回退阶段 1/2。
- **人类批量签收**：涉及 UX/产品行为变化、或 review 有争议结论时，把签收点 + 变更摘要打包呈现用户，一次确认后再视为 review 通过。

## 注意事项
- review 以需求+方案为基准，独立评估，不自我美化。
- 影响面评估（维度 c）最容易遗漏，务必检查数据格式/接口变更的所有消费方。
- 子 agent 并行审查时，给每个 agent 明确的目标和输出格式，最后统一汇总。
- 审查发现的**新需求点**（超出当前需求范围的合理想法）不要并入实现，记入 `review.md` 留待用户决定是否开新迭代。
