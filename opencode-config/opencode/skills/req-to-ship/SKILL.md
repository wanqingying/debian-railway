# ReQ-to-Ship — 全流程需求开发

分支、提交、push、PR 与合并遵循项目自身的 git 规范（若有贡献指南或 agent 流程文档则以它为准）；本 skill 在其之上补充需求开发流程，不重复定义这些规则。

本 skill 指导一次**完整的需求开发交付**，定位是**人机协同**：agent 像一名资深工程师伙伴，主动推进工作流、执行代码，把决策点批量收集起来让人类一次性拍板。它强调**批量协作**——agent 先把自己能做的做完，人类只做必须由人做的高价值决策，且尽量一次批量处理。

> 铁律：**决策权在人**。涉及范围、选型、破坏性操作、上线的决策必须由人类做出；agent 负责执行、建议和记录，不擅自替人决定。但 agent 不因待决点而空等——先按推荐继续，批量等待人拍板。

## 人机协作机制（本 skill 的核心原则）

### 核心模式：批量协作，而非逐步确认

**人类不会一直盯着 AI 工作，可能离开一段时间。** 因此默认模式是：**agent 自主推进，把必须问人的决策点收集成"待决清单"，到阶段边界一次性批量呈现给人类拍板**。不要每一步都停下等确认——那是低效的。

- **阶段内**：agent 自主完成该阶段能做的所有工作（研究、草案、方案、实现），遇到"必须问人"的决策点，不阻塞推进——先按**推荐方案**继续，同时把该决策加入待决清单，说明选项、推荐与理由。继续推进只覆盖在 review 前可逆的工作；破坏性操作、上线、写线上数据、超出常规验证的开销，都要等人类决策。
- **阶段边界**：把一个阶段的全部待决点**打包**呈现给人类（选项 + 推荐 + 理由），人类一次性拍板，agent 根据决定修正或继续。
- **不必等人类回来就停顿**：只要待决点不阻塞后续工作，就继续推进；只有**关键阻塞点**（如范围未定、方向性选择影响后续所有工作）才真正停下等。
- 如果任务简单（用户只说"做吧"），可以更自主：完成更多阶段后一次性汇总确认。

### 决策分层：什么必须问人、什么自主推进、什么主动汇报

| 层级 | 情形 | 示例 | agent 行为 |
|------|------|------|-----------|
| **必须问人** | 决策权在人，agent 不得擅自决定 | 需求范围、产品行为、技术选型、破坏性操作、上线/发布、涉及权限/数据/费用的改动 | 记入待决清单，阶段边界批量呈现，给"选项 + 推荐 + 理由"，等人拍板 |
| **自主推进** | 执行细节，决策权在 agent | 实现细节、命名、错误处理、测试用例写法、文档格式 | 自主决定；**把决策与理由留档备查**（见「文档」一节） |
| **主动汇报** | 不需决策，但人需要知情 | 完成一个逻辑单元、测试结果、进度变化、发现的风险 | 主动汇报（可批量：阶段结束时汇总） |

### 怎么批量呈现待决点（给人类省时间）
- 待决清单按**决策点编号**列出：每个含**问题背景 + 候选选项 + 推荐项 + 理由**，让人做选择题。
- 一次集中呈现，标注哪些是**阻塞项**（必须先定）、哪些可**后置**（不阻塞继续）。
- 问题带上下文、具体明确，不让人猜你在问什么。

### 人类需要动手的节点（agent 主动提示，不默默跳过）
- **阶段 1 边界**：一次批量拍板——范围/优先级 + 技术选型 + 关键调研结论认可。
- **阶段 3 边界**：review 签收——尤其 UX/产品行为变化。
- **阶段 4**：本地联调——需要真实环境/账号/手工验证时，明确请求用户执行并给出步骤。
- **合并**：工作完成时 agent 提交处于可 review 状态的 PR；合并需等待用户明确 LGTM。
- **人类确认点数量随级别调整**：L0 保留多个关键确认点（范围、选型、核心危险变更的上线/回滚决策）；L2 尽量合并为一次甚至不打断。

## 改动级别与流程深度（L0/L1/L2）

**先定级别，它决定后续一切工作的严格度**：测试深度、review 深度、回滚方案、人类确认点。它不决定要写多少文档——那由下方「文档」一节决定。级别从需求理解出发做初判，在技术方案阶段结合实际改动范围与影响面**确认或修正**（需求看着小、实际改动大是常态）；级别存疑时按**更高一级（更谨慎）**处理。记录级别与理由。级别越低越应精简流程，避免给无害改动套上重流程。

| 级别 | 定义 | 典型信号 | 流程深度 |
|------|------|----------|----------|
| **L0** | 大范围 / 底层框架 / 核心改动 | 跨模块、跨服务、多系统；底层框架、架构、核心抽象变更；数据模型或 DB schema 迁移、数据迁移；核心 agent/引擎/协议；影响面大、难以回滚；广泛涉及数据/权限/费用 | 强化：需求与方案必须做全；核心流程单测+e2e 必须覆盖；三维 review（可并行子 agent）；**必须**灰度/回滚方案；关键决策保留多个人类确认点 |
| **L1** | 新功能 / 功能增强 | 新的用户可见功能或明显增强；新增接口/UI 流程；涉及若干文件但边界清晰、可回滚；无数据模型迁移、无核心框架变更 | 四阶段，按需精简；覆盖核心路径的测试；标准三维 review；灰度/回滚**按需**（触及核心危险变更时必做） |
| **L2** | 小改动 / 有界改动 | 单功能内几百行以内的修复或调整：bug 修复、文案、样式/布局微调、配置值、prompt 措辞、新增枚举或词表值、依赖小版本升级；无 schema 变更、无破坏性契约变更；revert 即可回滚 | 走下方 L2 快速通道；定向测试 + 能证明改动的验证（输出/行为/费用有变化时给前后对比）；轻量 review；通常**不需要**灰度/回滚 |

**如何判定**（逐项过一遍）：
1. **影响面**：涉及多少模块/服务/系统？是否跨边界？
2. **契约与数据结构**：是否改动数据模型、DB schema、对外接口契约？
3. **底层**：是否触及框架、架构、核心抽象、核心引擎？
4. **可回滚性**：出问题能否快速、无损回滚？
5. **风险域**：是否涉及数据完整性、权限、安全、费用？

命中第 2/3/5 项且影响面大 → L0；新增功能但边界清晰 → L1；仅修复或有界调优（文案/样式/配置/prompt/新增取值）→ L2。无论大小，涉及权限/访问控制、安全控制、客户计费，或可能丢失/损坏数据的写入，至少为 L1。仅影响模型费用或输出质量时，提升的是你应给出的证据（前后对比），而非级别。测试覆盖、review 深度、灰度回滚需求、人类确认点都随级别调整。

### L2 快速通道

L2 不必走完整四阶段，按轻量流程即可：**理解需求与影响（codegraph 快查）→ 实现 → 定向测试 + 能证明改动的验证 → 提交处于可 review 状态的 PR，并在描述中写明这些证据**。跳过多轮批量边界（"必须问人"的决策仍要交给人类）；若改动触及了非预期的契约/底层/风险域，**立即升级级别**按对应流程补做。仍需保留两条铁律——不超出项目 git 规范所允许的范围 push 或合并、决策权在人——并确保工作区已建索引后再依赖 codegraph（见「工具操作速查」）。

## 全局原则（适用于所有阶段）

1. **代码分析以 codegraph 起步、以源码收尾。** `codegraph_explore` 是做定位的第一调用——调用链、符号、模块逻辑——但它的回答只是*起点*，不是全貌：跨包或跨语言的流程，若不点名文件，它通常只返回一侧。在把要改动的模块写进方案前，用 `rg` 确认写入方和调用方，并在修改前先读该文件。「工具操作速查」里有两类能提高召回率的提问习惯。
2. **确保工作区已建索引。** 索引是按目录的：新 worktree 没有 `.codegraph/`，需先在那里执行一次 `codegraph init --yes`。此后文件监听器会在每次保存时同步、服务器在连接时对账，所以无需再记同步步骤——切分支、rebase、pull 都会被当作文件变更处理。
3. **不假设、不隐藏困惑**：有歧义时不替用户做决定——属于"必须问人"的记入待决清单（按批量协作处理），其余按推荐自主推进并记录；不要默默猜测。
4. **文档按改动大小裁剪**：默认 PR 描述即记录，只有真正大型的工作才写迭代文档（见「文档」）。
5. **不超出项目 git 规范所允许的范围 push 或合并。** 一个实现请求涵盖提交、push 和处于可 review 状态的 PR；合并需要用户明确 LGTM。
6. **批量汇报**：完成一个阶段（或用户离开前），把进度 + 待决点打包汇总，不零散打扰；人类回来后一次性处理。

## 文档（按改动大小裁剪）

级别决定严格度；本节决定写什么。默认**不新建文档**：PR 描述与 commit 记录就是记录。只有当后续会话会丢失某些非显而易见的东西时，才写迭代文档——一个决策及其*原因*、一个坑、一个不变量、一个契约。

- **默认：PR 描述即记录。** 几百行以内的修复和改动（含 prompt、配置、费用、新增词表值等）不建迭代目录。除项目 git 规范要求 PR 描述的内容外，描述里还要带上：证据、验证（命令及其结果；输出/行为/费用有变化时给前后对比表）、带理由的决策、以及遗留风险，使 reviewer 无需对话就能看懂。
- **commit 记录即实现记录。** 不存在实现追踪文档。每个逻辑步骤一次提交，配语义化信息（按项目 git 规范），让 `git log` 与 `git blame` 承载"做了什么、何时做的"；迭代记录只在需要时引用一次提交区间，不列逐步 SHA 表。
- **仅对真正大型的工作写迭代文档**：schema 变更或迁移、跨模块/跨服务改动、新产品面、新增或破坏性对外契约、难以回滚的改动。当改动处于边界情形（小但命中上述清单，或大但不在清单内）时，先问用户再写。需要写时是**两个文件，不是四个**：
  - `design.md` —— **需求与技术方案合为一篇**；
  - `README.md` —— **迭代记录**：改了什么、为什么，带理由的决策，review 结论，遗留事项，状态。
- **非显而易见的知识应落在可被检索之处。** 调试配方、值得记住的根因、或一个决策及其*原因*，要写进仓库的文档（`ops/` 指南、迭代记录、或决策记录），而不只是 PR 描述——后续会话读的是仓库，不是 PR 讨论串。
- **遵循项目既有的文档约定**：`docs/` 下任何新文档的位置、命名、以及项目若使用的 frontmatter/元数据，都应照其约定，以便日后能被找到和筛选；项目没有约定时，有标题和日期即可。
- **遗留事项**（本次改动未修复的发现）写进 feature README 的 **Follow-ups** 列表，每条一两行——不单独建追踪文件。feature 没有 README 时，写进 PR 描述。
- **气味测试，而非预算**：除非是 L0，仓库文档行数不应超过它所描述的代码行数（prompt 与随仓库发布的 skill 算代码）。若会超过，把内容挪进 PR 描述。
- **不做无关的文档清理。** 只更新因你的改动而过时的文档，并把长期约束的原因放在代码旁（注释，或项目的编码规范文档）；其余留给各自的 PR。

需要写迭代文档时，与代码一起提交。先读 feature README 及其最近一次迭代，不要另造位置或命名：

```
docs/<feature>/
├── README.md                 # feature 入口：它是什么、指向 iterations/、Follow-ups 列表
├── user-guide.md             # 可选，跨迭代共享
├── ops/                      # 可选，长期有效的指南（runbook、调试指南）
└── iterations/NN-<slug>/     # 00-initial，之后每次大型改动一个新编号目录
    ├── design.md             # 需求 + 技术方案（含测试设计，需要时含发布/回滚）
    └── README.md             # 迭代记录：改了什么/为什么、决策、review 结论、遗留事项、状态
```

## 阶段总览与流程

**核心循环**：review 发现问题 → 回到阶段 2 修复；若问题源于需求/方案本身 → **允许回退**到阶段 1 修正，再继续。回退不当作失败，是正常的人类开发节奏。**推进节奏**：agent 自主推进 + 决策批量确认，不逐步停顿。

| 阶段 | 动作 | 交付物 | 人类参与点（批量） | 进入下一阶段 |
|------|------|--------|-------------------|-------------|
| 1. 需求澄清与技术方案设计 | 理解需求并结合现有代码细化；做架构+细节设计，调研关键依赖，review 方案 | 就绪的范围、方案与测试计划（仅当本次工作有迭代时才落 `design.md`） | 边界一次性批量拍板：范围/优先级 + 选型 + 关键调研结论 | 待决点打包确认后 |
| 2. 执行代码变更 | 建需求分支，确认 git 状态，实现代码（自主推进+记录决策） | 代码 + 测试 | 关键阻塞决策；实现要点可批量汇总展示 | code review 判定完成 |
| 3. 执行 code review | 三维审查：需求符合+功能 / 架构 / 影响面 | 问题修复；结论入记录 | 批量签收：review 结论、UX/产品行为变化 | review 通过；否则回到 2/1 |
| 4. 自测联调与交付 | 同步+测试+联调，交付待 review | 检查通过；PR 处于可 review 状态，证据写入其中 | 本地联调（给步骤）；LGTM | 用户明确 LGTM 后合并 |

每个阶段的**深度随改动级别（L0/L1/L2）调整**——级别的判定与流程映射见上文「改动级别与流程深度」。

## 各阶段入口

每个阶段有独立文档，含细则、模板和注意事项——开启对应阶段时读取：

- **阶段 1 需求澄清与技术方案设计** → 读 `references/01-requirements-and-design.md`
- **阶段 2 执行代码变更** → 读 `references/02-code-changes.md`
- **阶段 3 执行 code review** → 读 `references/03-code-review.md`
- **阶段 4 自测联调与交付** → 读 `references/04-test-and-delivery.md`

## 工具操作速查

### codegraph（代码分析）

```bash
codegraph status                                      # 当前 worktree 是否已建索引？（索引是按目录的）
codegraph init --yes                                  # worktree 没有 .codegraph/ 时执行一次；之后由监听器同步
codegraph explore "<问题，或符号/文件名>"              # 与 codegraph_explore MCP 工具输出一致
codegraph callers <symbol> -l 500                     # 默认截断在 20 条且不提示截断
```

- **用问题定位，用名称钉住。** 自然语言查询按关键词排序，并附上一堆检查脚本；把你关心的文件或符号名写进去，就能把它们钉进答案，也是跨包流程另一侧能出现的前提。
- **explore 的回答只是起点。** 在写入方案前用 `rg` 确认写入方和调用方，并在修改前先读文件。它对影响面的计数会低估通过命名空间（如 `namespace.member`）触达的部分，不要把它当作影响面结论引用。
- **CLI 未安装？** 按路由的工具回退规则处理（`rg`、读文件）——在记录中说明，并且绝不要声称做过你没运行的 codegraph 调研。

### 查找项目既有知识（docs）

设计前先找已有的，而不是重新推导：

```bash
cat docs/index.md                 # 项目若维护 docs 索引/地图则读它
rg -n "<term>" docs/              # 全语料关键词搜索（快、准）
```

- 从 docs 索引（若有）定位所属区域，再读 feature 的 `README.md`、其最近一次迭代、以及 `ops/` 下的指南。既有决策可能记录在决策记录中。
- **语义搜索是可选的。** 若 PATH 上有 `qmd`，用 `qmd query --no-rerank "<问题>"` 对 docs 做自然语言问答。若未安装 `qmd`，打印一行说明"语义搜索不可用"并继续用 `rg`——**绝不要因此阻塞阶段**。当它可用时，把标记为归档/已废弃的文档视为历史而非当前。

## 注意事项（高频坑）

1. **先定改动级别（L0/L1/L2）**：级别决定测试深度、review 力度、是否需要灰度/回滚、人类确认点多少。别给无害小改动套重流程，也别在核心改动上偷工；需求看着小、实际改动大时按更高级别处理。
2. **不要在阶段 1 就写生产代码**。需求未澄清、方案未 review 就动手，返工概率极高（允许 spike 验证）。
3. **代码 review 不能自己评自己**——review 时先读需求+方案，用 git 看变更，独立评估；必要时用 subagent 并行审查（见阶段 3 文档）。
4. **测试在方案阶段就定**（阶段 1 B7）；实现时照着写，不是实现完再补。
5. **不擅自扩大范围**：实现中发现方案没覆盖的新问题，先记录下来并向用户汇报、请示，不要默默追加实现。

## 兜底原则

- 用户说"只做个简单改动/别搞流程了/太复杂"，或任务明显是 trivial（改文案、修一处 bug、单文件小改动）时，按 **L2**（快速通道）处理，除非命中「如何判定」里的至少 L1 下限；但**保留两条铁律：不超出项目 git 规范所允许的范围 push 或合并 + 决策权在人**。
- 连续三轮在实现/自测卡住时，停止改代码，重新质疑假设（需求理解、方案本身、环境问题），先澄清再继续。
