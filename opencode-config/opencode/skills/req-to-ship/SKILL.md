# ReQ-to-Ship — 全流程需求开发

本 skill 指导一次**完整的需求开发交付**，定位是**人机协同**：agent 像一名资深工程师伙伴，主动推进工作流、产出文档、执行代码，把决策点批量收集起来让人类一次性拍板。它强调**批量协作**——agent 先把自己能做的做完，人类只做必须由人做的高价值决策，且尽量一次批量处理。

> 铁律：**决策权在人**。涉及范围、选型、破坏性操作、上线的决策必须由人类做出；agent 负责执行、建议和记录，不擅自替人决定。但 agent 不因待决点而空等——先按推荐继续，批量等待人拍板。

## 人机协作机制（本 skill 的核心原则）

### 核心模式：批量协作，而非逐步确认

**人类不会一直盯着 AI 工作，可能离开一段时间。** 因此默认模式是：**agent 自主推进，把必须问人的决策点收集成"待决清单"，到阶段边界一次性批量呈现给人类拍板**。不要每一步都停下等确认——那是低效的。

- **阶段内**：agent 自主完成该阶段能做的所有工作（研究、草案、方案、实现），遇到"必须问人"的决策点，不阻塞推进——先按**推荐方案**继续，同时把该决策记入待决清单（`review.md` 或临时待决清单），说明选项、推荐与理由。
- **阶段边界**：把一个阶段的全部待决点**打包**呈现给人类（选项 + 推荐 + 理由），人类一次性拍板，agent 根据决定修正或继续。
- **不必等人类回来就停顿**：只要待决点不阻塞后续工作，就继续推进；只有**关键阻塞点**（如范围未定、方向性选择影响后续所有工作）才真正停下等。
- 如果任务简单（用户只说"做吧"），可以更自主：完成更多阶段后一次性汇总确认。

### 决策分层：什么必须问人、什么自主推进、什么主动汇报

| 层级 | 情形 | 示例 | agent 行为 |
|------|------|------|-----------|
| **必须问人** | 决策权在人，agent 不得擅自决定 | 需求范围、产品行为、技术选型、破坏性操作、上线/发布、涉及权限/数据/费用的改动 | 记入待决清单，阶段边界批量呈现，给"选项 + 推荐 + 理由"，等人拍板 |
| **自主推进** | 执行细节，决策权在 agent | 实现细节、命名、错误处理、测试用例写法、文档格式 | 自主决定，**把决策和理由记录到 `review.md`**（可追溯） |
| **主动汇报** | 不需决策，但人需要知情 | 完成一个逻辑单元、测试结果、进度变化、发现的风险 | 主动汇报（可批量：阶段结束时汇总） |

### 怎么批量呈现待决点（给人类省时间）
- 待决清单按**决策点编号**列出：每个含**问题背景 + 候选选项 + 推荐项 + 理由**，让人做选择题。
- 一次集中呈现，标注哪些是**阻塞项**（必须先定）、哪些可**后置**（不阻塞继续）。
- 问题带上下文、具体明确，不让人猜你在问什么。

### 人类需要动手的节点（agent 主动提示，不默默跳过）
- **阶段 1 边界**：范围、优先级拍板。
- **阶段 2 边界**：选型拍板、关键调研结论认可。
- **阶段 4 边界**：review 签收——尤其 UX/产品行为变化。
- **阶段 5**：本地联调——需要真实环境/账号/手工验证时，明确请求用户执行并给出步骤。
- **上线**：用户明确表达"完成/上线/发布"意图后，agent 才执行提交+push+创建 MR。

## 全局原则（适用于所有阶段）

1. **分析代码优先用 codegraph 工具**。理解调用链、搜索符号、查模块逻辑时，用 `codegraph_explore`（CLI 用法见下），不要先 grep 猜。
2. **codegraph 同步时机**：需求开始前、切换分支后、同步远程代码后，都必须先执行代码变更同步（见下），保持索引新鲜。
3. **不假设、不隐藏困惑**：有歧义停下来问，不替用户做决定；决策分层表格决定怎么问。
4. **文档保留**：每个阶段的产出文档都落在项目的 `docs/` 目录，与代码一起提交，形成可追溯记录。
5. **未经用户明确指令，禁止 push 代码**。用户表达"完成/上线/发布"意图后，才做最后同步+提交+push+创建 MR。
6. **批量汇报**：完成一个阶段（或用户离开前），把进度 + 待决点打包汇总，不零散打扰；人类回来后一次性处理。

## 文档目录结构规范（全局约束）

项目的 `docs/` 下按需求组织，**以迭代（iteration）为演进单元**，参考 claude-mcp 的结构。**这是所有阶段 ref 文档必须遵守的约束**，任何阶段产出文档都必须落在下面规定的确切位置与命名，不得另起结构或自定义文件名。

```
docs/<feature>/
├── README.md              # 索引：迭代 timeline（# | 迭代 | 日期 | 内容 | 状态）、导航
├── user-guide.md          # 用户指南（可选，跨迭代共享；阶段2联调指南面向用户的部分可放此）
├── iterations/
│   ├── 00-initial/        # 首次需求迭代（基线）
│   │   ├── README.md      # 该迭代的需求变更、决策、状态（链接到下述文档）
│   │   ├── requirements.md        # 需求文档（阶段1交付）
│   │   ├── technical-design.md    # 技术方案文档（阶段2交付）
│   │   └── review.md              # 方案/code review 记录（阶段2/4交付）
│   ├── 01-<slug>/         # 后续需求迭代：每次需求变更开新目录，编号递增
│   │   └── README.md      # 该迭代的需求变更、决策、状态（比照 00 的结构）
│   └── ...
└── ops/                   # 跨迭代共享文档
    ├── implementation-tracking.md   # 进度追踪（逐条记录实现步骤+commit SHA）
    ├── launch-checklist.md          # 上线 checklist（阶段2产出，按迭代/上线批次组织）
    └── debug-guides.md              # 本地/线上联调指南（阶段2产出，阶段5使用）
```

**迭代凝聚力原则**：每个迭代目录持有该迭代的**全部**文档（需求、方案、review），并随迭代演进；跨迭代共享的文档放 `ops/`。**每次需求变更都新开一个编号递增的迭代目录**（`00-initial` 为基线，之后 `01-*`、`02-*`…），README timeline 按顺序追加，使演化可回溯。

**位置映射**：阶段 1 → `iterations/NN-*/requirements.md`；阶段 2 → `iterations/NN-*/technical-design.md` + `review.md` + `ops/launch-checklist.md` + `ops/debug-guides.md`；阶段 4 → 追加到该迭代的 `review.md`；阶段 5 → 更新 `ops/implementation-tracking.md`。当前迭代指需求文档所属的迭代目录。

**约定**：
- 新迭代：在 `README.md` timeline 追加一行（迭代号、日期、内容、状态），并新建 `iterations/NN-<slug>/README.md`（需求变更、决策、状态）。
- `ops/implementation-tracking.md` 逐条记录"哪一步、哪个 commit 落地"，与代码同 commit 更新（先 `git rev-parse HEAD` 记录基线 SHA 再 commit）。
- 各阶段 ref 文档只写**内容模板与步骤细则**，文档的**存放位置和命名一律以本规范为准**，ref 内不得重复定义目录结构。

## 阶段总览与流程

**核心循环**：review 发现问题 → 回到阶段 3 修复；若问题源于需求/方案本身 → **允许回退**到阶段 1 或 2 修正，再继续。回退不当作失败，是正常的人类开发节奏。**推进节奏**：agent 自主推进 + 决策批量确认，不逐步停顿。

| 阶段 | 动作 | 交付物 | 人类参与点（批量） | 进入下一阶段 |
|------|------|--------|-------------------|-------------|
| 1. 需求澄清与初始化 | 理解需求，结合现有代码细化，产出需求文档 | `iterations/NN-*/requirements.md` | 边界时批量拍板：范围/优先级/产品行为 | 待决点打包确认后 |
| 2. 技术方案设计与 review | 架构+细节设计，调研关键依赖，review 方案 | `iterations/NN-*/technical-design.md` + `review.md` + `ops/` 共享文档 | 边界时批量拍板：选型、关键调研结论 | 待决点打包确认后 |
| 3. 执行代码变更 | 建需求分支，确认 git 状态，实现代码（自主推进+记录决策） | 代码 + 进度追踪更新 | 关键阻塞决策；实现要点可批量汇总展示 | code review 判定完成 |
| 4. 执行 code review | 功能/架构/影响面三维审查 | `review.md`（追加，commit 级） | 批量签收：review 结论、UX/产品行为变化 | review 通过；否则回到 3/1/2 |
| 5. 自测联调与交付 | 同步+测试+联调，上线交付 | 测试通过，提交+push+MR | 本地联调（给步骤）、上线意图 | 用户表达上线意图后交付 |

## 各阶段入口

每个阶段有独立文档，含细则、模板和注意事项——开启对应阶段时读取：

- **阶段 1 需求澄清与初始化** → 读 `references/01-requirements.md`
- **阶段 2 技术方案设计与 review** → 读 `references/02-technical-design.md`
- **阶段 3 执行代码变更** → 读 `references/03-code-changes.md`
- **阶段 4 执行 code review** → 读 `references/04-code-review.md`
- **阶段 5 自测联调与交付** → 读 `references/05-test-and-delivery.md`


### 需求开发流程中的关键检查点

- 阶段 1 前：`codegraph sync`
- 阶段 3 建分支/切分支后：`codegraph sync`
- 阶段 3/5 同步远程后：`codegraph sync`
- 分析代码：`codegraph_explore` 工具（语法树调用图，优先于 grep）

## 注意事项（高频坑）

1. **不要在阶段 1/2 就写代码**。需求未澄清、方案未 review 就动手，返工概率极高。
2. **代码 review 不能自己评自己**——review 时先读需求+方案，用 git 看变更，独立评估；必要时用 subagent 并行审查（见阶段 4 文档）。
3. **push 是受控动作**：只有用户表达完成/上线/发布意图后才执行最后的提交+push+创建 MR。
4. **需求变更要更新进度追踪**：实现步骤在 `ops/implementation-tracking.md` 里逐条打勾并记录 commit SHA。
5. **方案中的关键调研不能跳**：技术方案里"关键技术调研"和"架构对比评估"是必填项（无新依赖可写"N/A 无新依赖"，无架构分歧可写"无"并说明理由），不能整个省略。
6. **e2e/单测设计放在方案阶段就做**（阶段 2 交付物之一），实现时照着写，不是实现完再补。
7. **不擅自扩大范围**：实现中发现方案没覆盖的新问题，先记入 `review.md` 并向用户汇报、请示，不要默默追加实现。

## 兜底原则

- 用户说"只做个简单改动/别搞流程了/太复杂"，或任务明显是 trivial（改文案、修一处 bug、单文件小改动）时，可跳过/大幅简化文档流程，但**保留 codegraph sync + 不擅自 push + 决策权在人 三条铁律**。
- 连续三轮在实现/自测卡住时，停止改代码，重新质疑假设（需求理解、方案本身、环境问题），先澄清再继续。
