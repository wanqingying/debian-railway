## Project

Debian Bookworm Slim container deployed on Railway as a **remote dev container**. Access:
- **SSH** (primary, for VS Code Remote-SSH) on `$PORT`
- **OpenChamber** web UI (auto-manages an embedded **opencode** server) on `OPENCHAMBER_PORT` (`3001` by default)
- **opencode** headless server (HTTP, basic auth) on `OPENCODE_PORT` (`4096`), managed by OpenChamber, bound to `127.0.0.1`
- **ttyd** web-terminal (optional) on `$TTYD_PORT`

No build/test/lint toolchain — the Dockerfile + entrypoint script are the whole app.

## Commands

- Deploy to Railway: `railway up` (after `railway login` / linking). No local build or test step.
- Local build/test (from README):
  ```bash
  docker build -t debian-dev .
  docker run --rm -p 22:22 -p 4096:4096 \
    -v /tmp/ws:/workspace \
    -e SSH_PUBLIC_KEY="$(cat ~/.ssh/id_ed25519.pub)" \
    -e PORT=22 debian-dev
  ```
  (`-v /tmp/ws:/workspace` simulates the Railway volume so opencode state persists.)
- Railway CLI reference: `docs/railway-cli.md` (linked from README). Consult it before running CLI commands instead of guessing flags.

## Architecture

- **`entrypoint.sh`** is the container's `CMD` (Dockerfile:104), run as PID 1 under **`tini -s`** (Dockerfile:103) so orphaned children are reaped instead of accumulating as zombies (see the Dockerfile gotchas). It bootstraps the `/workspace` volume from baked config, sets the SSH port, injects `SSH_PUBLIC_KEY`, applies `PASSWORD`, starts `sshd`, conditionally starts ttyd, runs `/scripts/install-tools.sh` (app toolchain), migrates a v1 opencode session db if present, drops the pinned `@latest` plugin cache, then starts `openchamber serve` **as a daemon** (deliberately not `--foreground` — see the update note below) (**which spawns its own embedded `opencode serve`** — opencode is not started separately), then starts the **interactive browser** (`/scripts/start-browser.sh`, unless `BROWSER_ENABLE=0`), then detaches the **Feishu Q&A bridge** (`/scripts/start-feishu-bridge.sh`, unless `FEISHU_BRIDGE_ENABLE=0`). It keeps the container alive with `exec tail -f /dev/null`.
- **`scripts/install-tools.sh`** (baked to `/scripts/install-tools.sh`) — idempotent dev-toolchain bootstrap run at every start: apt packages (ffmpeg/lsof/unzip/jq/build-essential/fonts), `uv` + Python 3.12, pnpm 11.22.0 via corepack, Doppler CLI, Railway CLI, GitHub CLI (`gh`, from GitHub's official apt repo), **OpenChamber** (the fork's 2.7.0 build, baked from `vendor/openchamber-web-2.7.0-fork.tgz` → `/opt/openchamber-fork/`) + **OpenCode v2** (`@opencode/cli` @2.2.6), both **pinned** (env-overridable; see the version-pair note under the upgrade notes), plus repair of a persisted `core/.venv` if present. Root-FS installs are wiped each redeploy, hence re-run on boot. OpenChamber and OpenCode versions must stay matched: the 2.7.0 we run declares `MINIMUM_OPENCODE_VERSION = 2.2.4`, and installing v1 `opencode-ai` makes OpenChamber report `Configured OpenCode binary not found` and run with no agent.
- **Persistence** is via the mounted Railway volume `/workspace`. `XDG_DATA_HOME=/workspace/.opencode/data` and `XDG_CONFIG_HOME=/workspace/.opencode/config` redirect **opencode and magic-context** state (sessions db, auth, memories), and `OPENCHAMBER_DATA_DIR=/workspace/.opencode/config/openchamber` redirects **OpenChamber's own** state (settings, preferences, projects, themes, managed chats) — OpenChamber otherwise defaults to `~/.config/openchamber`, which it does not move for `XDG_CONFIG_HOME`. `entrypoint.sh` then symlinks `~/.config/openchamber` to that directory so the few auxiliary writers that hardcode the default path (managed-process registry, telemetry install id) also persist. All of it survives restarts; `/root` is ephemeral.
- **magic-context** is configured (user-level) at `opencode-config/cortexkit/magic-context.jsonc` → `$XDG_CONFIG_HOME/cortexkit/magic-context.jsonc`, with its store at `$XDG_DATA_HOME/cortexkit/magic-context/context.db` (on the volume; ~270 MB and growing). The plugin itself is **pinned to `0.49.43`** in `opencode.jsonc`'s `plugins` (see the version-pair note). Four things to keep straight:
  - **Two different `compaction` keys, two different files.** `compaction.auto: false` in `opencode.jsonc` turns OFF OpenCode's native compaction; `compaction.enabled: true` in `magic-context.jsonc` is magic-context's own switch saying MC owns the window. Both are pinned so neither an upstream default change nor a cloned repo can hand the window back to native compaction.
  - **`fail_closed_blocking: true` is deliberate.** When MC cannot operate (schema fence after a version skew, storage open/migration failure) it blocks the primary turn with a loud recovery error instead of silently degrading to native compaction. A turn that dies with an unexplained "OpenCode interrupted this reply" is usually a blocked turn — run `npx @cortexkit/magic-context@latest doctor --harness opencode` to read the real reason.
  - **Hidden agents have no built-in fallback chain** (a failing primary is retried, never replaced), so the config carries explicit `fallback_models` for both the historian and the dreamer. `dreamer.tasks` lists every task explicitly, including two pinned OFF: `compress-cues` (serves only the experimental `mural`, which is off) and `maintain-docs` (our docs are hand-maintained in git).
  - **No boot-time housekeeping is needed any more.** MC requires **OpenCode ≥ 2.0.22** for hidden runs and deletes each dreamer/historian child through the native session API when the run ends, "whether or not the host runs as a service" — so `entrypoint.sh` no longer runs `doctor --fix`, which also removes the only automatic source of an orphaned `opencode serve --service` (~500 MB + its own codegraph MCP tree, holding both store files). Verified 2026-10-19 on OpenCode 2.0.32 + MC 0.49.12: historian and dreamer both ran after boot and created no new `metadata.magic_context = "hidden-run"` session. Rows from before 2026-10-12 are legacy children the doctor's recorded inventory can no longer reach; list them with `npx @cortexkit/magic-context@latest doctor list-hidden-sessions`.
- **Worktrees live on the volume** (`$WORKTREE_ROOT`, default `/workspace/worktrees`). A worktree *is* a session's working directory, so one created on the root filesystem is deleted by the next redeploy and its session then fails with `Directory not found: <path>` and cannot be resumed — measured once at 13 hours plus a lost uncommitted change. Three things keep it honest: `worktree.directory: "/workspace/worktrees"` in `opencode.jsonc` (absolute, so it holds for every project and also drives OpenChamber's own *New worktree* button — verified through `previewWorktreeCreate`: `/workspace/joops` + `{name:"api-selftest"}` → `/workspace/worktrees/api-selftest`), `scripts/worktree.sh` baked to `/scripts/worktree.sh` and symlinked to `/usr/local/bin/wt` at boot, which **refuses any root outside `/workspace`**, and a rule in the global `AGENTS.md` telling agents to use `wt` and never to `git worktree add` into `/tmp`, `/root` or `/var/tmp`. Changing the setting does not move existing worktrees; the legacy data-dir root (`$XDG_DATA_HOME/opencode/worktree/<projectID>/`) is still populated by older ones. Full runbook: `docs/worktrees.md`.
- **Config bootstrap**: non-sensitive config is baked into the image at `/opt/opencode-config/` (copied from host global config). On start, `entrypoint.sh` syncs it into `$XDG_CONFIG_HOME`, **overwriting volume files whose content differs** (the baked config is the source of truth) — so image config updates propagate on redeploy. Layout mirrors the target: `opencode-config/opencode/` → `$XDG_CONFIG_HOME/opencode/` (opencode reads its global config from the XDG app subdir, NOT from `$XDG_CONFIG_HOME` root — a flat layout is silently ignored), `opencode-config/cortexkit/` → `$XDG_CONFIG_HOME/cortexkit/` (magic-context plugin reads XDG root directly).
- **OpenChamber serve** runs the web UI on `OPENCHAMBER_PORT` (default 3001, bound `0.0.0.0`, UI password from `OPENCHAMBER_UI_PASSWORD` falling back to `OPENCODE_SERVER_PASSWORD`) in **daemon launch mode**, and writes its own log to `$OPENCHAMBER_DATA_DIR/logs/openchamber-<port>.log` (the shell redirect in `entrypoint.sh` only captures the startup banner; `openchamber logs` tails the real one). It manages an embedded **opencode serve** on `OPENCODE_PORT` (default 4096, bound `OPENCHAMBER_OPENCODE_HOSTNAME` default `127.0.0.1`), which keeps basic auth from the standard opencode envs: user `opencode`, password `qingying` (override with `OPENCODE_SERVER_USERNAME`/`OPENCODE_SERVER_PASSWORD`). OpenChamber proxies the opencode API through its own server.
- **Feishu Q&A bridge** — `scripts/start-feishu-bridge.sh`, started detached from `entrypoint.sh` right after OpenChamber. It is a **supervisor**, not the bridge: the bridge itself lives in the joops repo on the volume (`FEISHU_BRIDGE_ROOT`, default `/workspace/joops/feishu-bot`) and answers questions asked in an inspection report's Feishu topic with the session that wrote that report. The supervisor waits (≤90s) for the embedded opencode server to answer `/api/info`, runs `pnpm install --frozen-lockfile --ignore-scripts` when `package.json`/lockfile changed, then restarts `node src/bridge.ts` with capped exponential backoff (5s→300s). One `flock` keeps a single supervisor per container **and** the bridge holds its own lock: a second long connection to the same Feishu app does not error, it silently steals events. Log: `$XDG_DATA_HOME/feishu-bridge/bridge-supervisor.log`. Nothing here is started by hand — `/usr` is rebuilt on every redeploy, so anything not launched from `entrypoint.sh` disappears, and events sent while the bridge is down are lost (Feishu does not replay them).
- **Interactive browser (KasmVNC)**: `scripts/start-browser.sh` (baked to `/scripts/start-browser.sh`, called by `entrypoint.sh` after OpenChamber unless `BROWSER_ENABLE=0`) runs a real, windowed **Chromium** on a virtual X display, streamed to KasmVNC's built-in HTML5 VNC client, so a **manual sign-in** the agent cannot do alone (QR-code scan, CAPTCHA, 2FA, device pairing) can be completed by hand; the same browser exposes **CDP on `127.0.0.1:9222`**, so the agent then attaches to that *same* signed-in session. **Attach with `pw <cmd>`** (`scripts/pw` → `/usr/local/bin/pw`), which does an idempotent `playwright cli attach --cdp` and then runs the subcommand (`pw snapshot`, `pw click e15`, `pw eval "document.title"`): `playwright` 1.65.0 is installed globally (CLI + library, **no browser download** — we never run `playwright install`) and a `playwright-cli` shim makes the upstream commands work as written. **Never use `playwright cli open` for takeover**: it honours `~/.playwright/cli.config.json`'s `browser.cdpEndpoint` (written at boot) and does attach, but it runs `page.goto()` and navigates the user's live tab away (measured 2026-10-29). For scripts use the library: `connectOverCDP('http://127.0.0.1:9222', { noDefaults: true, isLocal: true })`. Its profile lives on the volume (`BROWSER_PROFILE_DIR`) so sign-ins survive a redeploy. `install-tools.sh` installs the pieces — apt (`chromium`, `chromium-l10n`, `fluxbox`, `fonts-noto-cjk`, `x11-utils`, `scrot`) plus a pinned KasmVNC `.deb` (not in Debian) — and `start-browser.sh` pins the UI language via `BROWSER_LOCALE` (`zh-CN`; Chromium on Linux takes the UI locale from `LANG`/`LANGUAGE`, so `chromium-l10n` is what makes a non-English UI possible). The view is served on `BROWSER_PORT` (`8444`), bound to `127.0.0.1` by default — reach it over the SSH tunnel. Full runbook: `docs/interactive-browser.md`; **self-check** (is it actually alive and windowed?): `docs/browser-self-check.md`.
- **OpenCode 2 / OpenChamber 2 upgrade notes** (applied 2026-09-24):
  - **Version pins**: OpenChamber is **this fork's build of 2.7.0**, installed from the tarball baked at `vendor/openchamber-web-2.7.0-fork.tgz` → `/opt/openchamber-fork/` (the 2.7.0 release + the `sidebarGroupRootWorktrees` "group worktrees" toggle; upstream #5669 is still open). It is not the npm package: npm's 2.7.0 has no fork patch, and the Dockerfile's build-time assertion fails if `groupRootWorktrees` is missing from the installed `dist`. Rebuild in `/workspace/openchamber-fork` on branch `fork/2.7.0` (tag `bd-003-2.7.0-fork` = upstream `v2.7.0` + the patch; `main` still sits on the 2.6.1 line): `bun install --frozen-lockfile`, `(cd packages/web && bun run build)`, `bun run pack:web`, then copy `packages/web/openchamber-web-2.7.0.tgz` over the vendor file and `railway up`. OpenCode is `@opencode/cli@2.2.6` (v2) from npm, pinned the same way. Both are **pinned**, not `@latest`: `latest` made every redeploy a coin flip, one bad upstream release silently takes the whole AI stack down, and the two must stay matched. The v1 package `opencode-ai` is no longer installed anywhere: OpenChamber 2.x requires OpenCode ≥2.2.4 in the 2.7.0 we run (`server/lib/opencode/compatibility.js` → `MINIMUM_OPENCODE_VERSION`) and will not fall back to v1. `scripts/install-tools.sh` keeps `OPENCHAMBER_VERSION`/`OPENCODE_VERSION` as env-overridable knobs (default `2.7.0`/`2.2.6`) and installs OpenChamber from `/opt/openchamber-fork/…tgz` (npm `@openchamber/web` only when that file is gone, which loses the patch), but the **Dockerfile's baked installs normally decide both versions** — `install-tools.sh` only installs when the binary is missing — so bump the pins in the same commit. (The `--allow-scripts` flag is not what provides the binary: measured on npm 11.19.1 the platform payload arrives as an optionalDependency that npm hard-links into `bin/`, so `opencode` runs either way; the flag only silences the install-scripts warning.) The `curl … | bash` installers are deliberately not used: they install under ephemeral `$HOME` (or pick pnpm/bun) and edit shell rc files, which a container that rebuilds `/usr` on every redeploy cannot rely on.
  - **magic-context is pinned to `0.49.43`** in `opencode.jsonc`'s `plugins` (BD-003). The earlier 0.49.34 pin existed because 0.49.35's **host fold** wrote an empty `<session-history></session-history>` compaction summary for **subagent sessions with no historian/history**, and OpenCode 2.2 then refused every turn with `Schema validation failed … Compaction requires either encrypted content or a summary` (upstream cortexkit/magic-context#838). #838 was closed on 2026-11-06 as completed, and the 0.49.36–0.49.43 line fixes that whole class: empty and missed folds, a `/compact` that reclaimed nothing, per-pass work that grew with the session, failed tool calls breaking the request schema, and obsolete instruction rows filling the context window. It also restores the host-fold speed-up (25k-message session: 1.3–2.0 s → 0.33–0.49 s/step). #834 (each pass copies the live history 2–3 times) is still open but no longer blocking. When bumping: change the spec here, change `MC_PLUGIN_CACHE_SPEC` in `entrypoint.sh` (it prunes cached builds that are not the pinned one), and re-validate `magic-context.jsonc` against that tag's `assets/magic-context.schema.json`.
  - **Pins this repo has carried, and why they are gone**: the 1.x line once hit an npm ETARGET on the OpenChamber SDK; OpenCode was pinned to 2.0.15 on 2026-09-25 for a reported 2.0.16 image-attachment regression (`Media.Asset` schema failure in `SessionModelRequest.prepare`, UI showing only "OpenCode stopped this reply"). That report is **not reproducible on 2.0.16**: the container that actually ran 2.0.16 accepted a user message with an inline PNG (`session_message.data.files[]`, 124 KB base64) and completed the turn, and `SessionModelRequest`/`Media.Asset` live only in the `@opencode/cli` binary (nothing in `@openchamber/web`). That pin was dropped; the current `2.2.6` pin is a deliberate anti-drift decision (see above), not a workaround for a known regression. If images ever break again, exercise the attachment path directly before blaming the version.
  - **Updates: the in-app button installs `@latest`, but a redeploy restores the pin.** OpenChamber self-updates only a **daemon** instance: `POST /api/openchamber/update-install` spawns a detached `npm install -g @openchamber/web@latest`, exits (freeing the port), and the script restarts `openchamber serve` with the same flags. A **foreground** instance is assumed to be systemd-managed and gets a 409 (`Set OPENCHAMBER_SYSTEMD_UNIT ...`) — and Railway offers neither systemd nor the updater's container branch (no `/.dockerenv`, no `CONTAINER` env), which is exactly why the 2.0.0 foreground container could not update from the UI. `/usr` is ephemeral, so an in-place update lasts only until the next redeploy — which re-installs the pinned version, so the button is now only a *temporary* override. On this image that override is worse than usual: the button installs upstream `@latest`, so the fork's worktree-grouping toggle disappears until the next redeploy. To actually change versions, bump the pins in `scripts/install-tools.sh` (and the Dockerfile's opencode line), for OpenChamber by replacing `vendor/openchamber-web-2.7.0-fork.tgz`, then redeploy.

    OpenChamber writes it into `$XDG_CONFIG_HOME/opencode/opencode.jsonc` when a provider is switched off in
    its settings UI — so a top-level `model` (or `agents.title`/`agents.summary`) pointing at a disabled
    provider fails with `Model unavailable: <provider>/<model>` (OpenChamber reports it as 503
    `small-model-unavailable` for title/summary). **Three providers are enabled here**: `opencode-go`,
    `a6api` and `gptge` (two reseller gateways; see the notes below). `disabled_providers` lists commandcode, deepseek,

    The `providers.commandcode.models` block is kept but inert while the provider is disabled.

    `https://a6api.vip/v1` (OpenAI-compatible). Its model ids are its own: `deepseek-v4.1-flash-1017` is the

  - **`opencode.jsonc` uses the v2 config shape**: `providers` (`package`/`settings.baseURL`/`modelID`/`capabilities`), `permissions`, `plugins`, `update`, `mcp.servers`, and title/summary models under `agents` (migrated 2026-10-26 from the deprecated v1 keys, which OpenCode 2 still *accepts* but no longer documents). Whatever shape is used, the file must stay free of retired v1 keys: one `configuration normalization diagnostic` (`kind=unsupported`) is emitted per retired key on **every** config/provider/model resolution. Carrying the v1-only fields (`provider.commandcode.models.*.release_date`/`reasoning`/`attachment` × 24 models, top-level `server`, `compaction.prune`) made the idle server log ~750 lines/s (~35 MB / 3 min) and hold both opencode processes at ~40%/~16% CPU. Those were removed 2026-09-24 and the provider still activates (verified). Re-add nothing retired.
  - **Only the v2 discovery paths exist** (verified against 2.1.4 by loading a probe file in each place): `$XDG_CONFIG_HOME/opencode/{skills,plugins,agents,commands}/` are read; **`tools/` is not** — a custom tool must be a plugin calling `ctx.tool.transform`, and the plugin SDK (`@opencode/plugin`) is supplied by the host, so a local plugin needs no `node_modules`. `tui.jsonc` is likewise dead (v2 reads `cli.json`). Files whose plugins are not in `plugins` (`dcp.jsonc`, `smart-voice-notify.jsonc`) and the v1 `tools/` tree were removed 2026-10-26 — `entrypoint.sh` prunes them from the volume, because the bootstrap copy never deletes.
  - **`CLAUDE.md` is ignored**: OpenCode 2 reads project instructions from `AGENTS.md` only. `opencode-config/` therefore ships no `CLAUDE.md`, and adding one would have no effect.
  - **Session db generation matters**: v1 dbs have `message`/`part` tables, v2 has `session_message`/`session_inbox`. The v2 core can still read a v1 db, but **magic-context refuses it** (`expected v2, found v1; refusing generation-specific database access`), which interrupts every turn silently (the UI only says "OpenCode interrupted this reply"). `entrypoint.sh` detects this via `node:sqlite` table names and renames the file to `opencode.db.v1-backup-<timestamp>` (keeping only the newest), so v2 recreates a fresh db. Both the core and the plugin hardcode the `opencode.db` filename, and the plugin ignores `OPENCODE_DB`, so relocating the db is not an option.
  - **Why the plugin spec is exact.** Below 0.43.0, attaching an **image** on OpenCode 2 killed the session — every subsequent turn failed with `Failed to drain Session: Error: Schema validation failed` (stack frame `SessionModelRequest.prepare`), text-only prompts included (upstream cortexkit/magic-context#517). The underlying trap is that opencode **caches** the version it resolved for a plugin spec (`~/.cache/opencode/npm/<pkg>@<spec>/<timestamp>/`) and never re-resolves a tagged spec, so an `@latest` entry could sit on a stale build indefinitely (observed on the dev container: 0.42.6 still in place while 0.45.0 was published). An exact spec removes that class of drift; `entrypoint.sh` additionally prunes any cached build that is not the pinned one, so an older pin left on a long-running container cannot be served. To check what is actually running: `node -e 'console.log(require(process.argv[1]+"/package.json").version)' "$(ls -d ~/.cache/opencode/npm/@cortexkit/opencode-magic-context@0.49.43/*/node_modules/@cortexkit/opencode-magic-context | head -1)"`.
  - **A `/skill` at position 0 works from OpenChamber 2.0.1 on** (it was broken in 2.0.0, upstream issue #3877). 2.0.0 routed any message whose first character is `/` through `POST /api/session/{id}/command`, but OpenCode 2's command endpoint resolves **only the command registry**, which is completely separate from the **skill registry** — so a leading skill name always 404'd with `Command not found: <skill>`. 2.0.1's chat router instead attaches a recognized skill to a normal prompt (`skills: [{id}]`, which injects the full skill body) — commit `61e6535`, PR #3895, plus `7f01569` "load skills live before routing a leading /skill". `/skill` mid-message (`请用 /req-to-ship 处理 …`) and the one-leading-space form (` /req-to-ship …`) still work. `opencode-config/opencode/commands/` stays intentionally absent — a command with the same name would shadow the native skill path, so no `/skill` wrapper commands.

## Dockerfile gotchas

- `ttyd` is pinned to `ttyd.x86_64` (Dockerfile:26) — x86_64 only. Fails on ARM builds; make arch-aware if ARM is ever needed.
- `EXPOSE $PORT` (Dockerfile:90) resolves at build time; set `PORT` as a build arg/env or Railway's default. openchamber port `3001`, opencode port `4096` and the interactive-browser port `8444` are also EXPOSEd.
- `SSH_PUBLIC_KEY` is injected by `entrypoint.sh` each start (so a key survives restarts without a volume). Without it, only password login works (needs `PASSWORD`).
- **SSH host key is persisted**: `entrypoint.sh` keeps one ed25519 **host** key on the volume (`$XDG_CONFIG_HOME/ssh`, generate-once) and points `sshd_config` at it (dropping the image's per-build keys), so the server fingerprint is stable across redeploys and clients (VS Code Remote-SSH, autossh) stop hitting `REMOTE HOST IDENTIFICATION HAS CHANGED`; a fresh volume still mints one new key.
- `entrypoint.sh` must stay executable (`chmod +x`) and keep `set -e`.
- **PID 1 must reap**: the image runs `entrypoint.sh` under `tini -s` (`ENTRYPOINT ["/usr/bin/tini","-s","--"]`, Dockerfile:103). Without it, the keep-alive `tail -f /dev/null` the entrypoint `exec`s into *is* PID 1 and never `wait()`s, so every orphaned descendant that exits (esbuild's service child, codegraph's watchdog, short-lived bash/grep) is re-parented to PID 1 and stays a **permanent zombie**. Zombies count against the cgroup `pids.max` (1000 here) and are never released, so in ~2 days every `fork()` fails with `EAGAIN` and even `git` cannot start — the container looks "stuck" until it is restarted (which is the only thing that clears them). Verified live in the container: an orphaned probe process left a zombie under a `tail` PID 1 and was reaped under `tini -s`. Keep tini as PID 1; do not drop the `ENTRYPOINT`.
- **Secrets are NOT in the image or repo**: `auth.json`/`account.json`/`opencode.db` (API keys, session history) are excluded from `opencode-config/`. Credentials must be provided at runtime via env vars or `opencode auth login`.

- `opencode-config/opencode/plugins/session-search/index.ts` + `opencode-config/opencode/lib/session-search.ts` — the `session_search` **tool**: cross-session recall. Given a keyword it answers "which past session dealt with this?" across every project on the machine — one row per session with id, title, directory, last activity, occurrence count and a short snippet. This is the one question no OpenCode or OpenChamber API can answer: `session.messages` can read a session once you know its id, but `session.list` has no query parameter, so finding one by content means walking 180+ sessions over HTTP. Registered as a **plugin** because OpenCode 2 has no `tools/*.ts` discovery path (the v1 mechanism; the `/docs/tools` page is the built-in catalog, authoring lives under `/docs/build/plugins`). Reads `opencode.db` **directly**, read-only, `node:sqlite`, Node ≥ 22 (below that it returns a one-line message instead of falling back). The path resolves exactly as `entrypoint.sh:103` does (`$XDG_DATA_HOME/opencode/opencode.db`, else `~/.local/share/...`), so one copy serves both containers — Railway sets `XDG_DATA_HOME=/workspace/.opencode/data`, a devcontainer leaves it unset. Searches user text and assistant `text` parts only: **tool output is excluded** (~19× the text volume and the densest place for secrets — the one change that would make redaction worth its cost, so revisit it if searching tool output is ever enabled). Output is **not redacted**, decided 2026-10-28 after measuring: the corpus held no real credentials (0 of 6,909 messages matched a provider-token, JWT, url-credential or private-key pattern), `session.messages` returns the same text unredacted so a rule in one read path was never a boundary, and both providers are internal gateways (`ada-cli-golang.ctripcorp.com`, `aigw.fx.ctripcorp.com`) rather than a third-party API — while masking did destroy the exact config values a "how is X configured" search exists to read. Performance rule — SQL `LIKE` prefilters the raw JSON and only matching rows are parsed; parsing all ~9k messages takes 2.2 s versus 55–180 ms prefiltered. Defaults exclude archived, subagent and `/tmp` sessions, and `match` defaults to **`both`** (titles + conversation): the title scan is a loop over ~100 in-memory rows, and a date only ever appears in a title ("巡检 2026-11-06 20:25"), so content-only default would make those unfindable. Rank is `matches + (title_match ? 1 : 0)` with the raw `time_updated` as tie-break — without the title weight a title-only hit sorted below every body mention and `limit` cut all of them (measured: 5/5 for "fork"); without the numeric tie-break, sessions updated in the same minute came back in arbitrary order, because `at` is truncated to the minute. **Fork copies are labelled, not dropped**: on 2026-11-14 the store held 17 forked children in a 101-session scope and 22–33% of every result set was a copy of a session already in it, but 16 of those 17 carried messages their parent does not (70–100% unique for most, since a fork diverges and keeps working) and 1–6 fork hits per query had no parent hit at all — so each hit carries `fork_of` + `fork_of_title` (falling back to the fork's own title, suffix stripped, when the parent was deleted) and the agent is told to read one of the pair, not both. The `(fork #N)` title suffix is stripped before title matching, because it made a search for "fork" return copies of unrelated sessions. `project` is the path below `/workspace`, not `basename` (14 of 26 directories shared a basename — "assistant" covered 12 sessions, "debian-railway" 23); the CLI shortens paths over 34 chars for alignment while JSON keeps them whole, and `--help` documents the options. **Multi-term search is the model's job, not the tool's** (2026-11-14): `query` is one literal substring, so a 17-character question returned 0 hits in all five measured cases, and `{"total":0}` reads exactly like "this never happened". The tool cannot split it: this SQLite has no ICU, FTS5 trigram needs 3 characters (2-character Chinese terms index nothing — 飞书/巡检/副本/用量 all fail), and a measured bigram splitter ranked unrelated sessions first ("worktree /tmp" → 我的世界抓取) because function-word bigrams (不算/为什么/不到) outrank the real terms even with IDF weighting. So the model passes `keywords` (1–6, over-limit refused with the limit named) plus `require: 'any'|'all'`; the tool does one scan with the terms OR'd in SQL and ranks by **coverage** (distinct terms a session contains) before raw occurrences, and `require:'all'` filters *after* scoring so an empty result can say "N sessions contain at least one — retry with require:'any'". Every zero-result answer carries a `hint` stating that matching is literal and not word-AND. Measured live: 2–4 terms cost 292–681 ms, inside the 2 s budget; a one-term search is unchanged (coverage 1 for every hit, so the old ordering holds). The lib is also a CLI (`node opencode-config/opencode/lib/session-search.ts <keyword> [--json]`), so the tool and the shell path cannot drift. Tests sit beside it (`session-search.test.ts`, run with `node --test`) against throwaway fixture databases — never the live store, which would make them rot within a day. The keyword is JSON-escaped before it becomes the `LIKE` pattern: without that, a query containing `"` or `\` matched nothing and the tool silently answered "no such session". A wall-clock budget (2 s) only ever cuts the JSON parse, never the answer: the `LIKE` scan runs inside one synchronous SQLite call so it cannot be interrupted anyway, and the first version checked the deadline after finishing the work and then discarded the hits — a cold-cache 83-hit search over `magic-context` answered "nothing". Exceeding the budget now stops the parse early and returns what was found with `truncated: true` (cold page cache costs ~1.4 s on this store, so this is a real path, not a theoretical one).

- `opencode-config/opencode/plugins/sysinfo/index.ts` + `opencode-config/opencode/lib/sysinfo.ts` — global opencode `sysinfo` tool so any agent can probe the current date/time and timezone, OS/distro/kernel/shell/user/locale, container/CI/railway flags, CPU/memory/disk, the active Python venv, and the installed developer tools with versions. **Resource numbers are the cgroup quota, not the host's**: `cpu`, `mem` and `limits` are read from the cgroup — v2 (`cpu.max`/`memory.max`/`memory.current`/`memory.peak`/`pids.max`), or on a v1 host from its per-controller hierarchies (`memory.limit_in_bytes`, `cpu.cfs_quota_us`/`cpu.cfs_period_us`, `pids.max`) — resolving this process's own cgroup from `/proc/self/cgroup`, so a host-root `/sys/fs/cgroup` mount is read correctly and a private cgroup namespace (`0::/`) falls back to the mount root. Unlimited sentinels (`max`, `-1`, v1's near-2^63 byte count) count as no limit, and when nothing readable is found the whole section is omitted rather than guessed. `limits.hostView` calls out the kernel's misleading host view — `os.cpus()`/`os.totalmem()` report the 48-core/323 GB host inside an 8-core/16 GB container, and sizing work from them oversubscribes ~6x. `container` gives PID 1 (`tini -s -- /entrypoint.sh`), its wall-clock start and uptime computed from `btime` + `/proc/1/stat` `starttime` (`/proc/uptime` counts the *host*'s boot, not the container's). `ports` lists env-configured ports (`*PORT`, Railway's excluded) and listening sockets from `/proc/net/tcp{,6}` split into `external` (bound to a wildcard address, so reachable from outside) and `loopback` (needs the SSH tunnel). `railway` carries project/service/environment/region/deployment/volume plus the public endpoints: `tcpProxy` (`RAILWAY_TCP_PROXY_DOMAIN:PORT -> RAILWAY_TCP_APPLICATION_PORT`, i.e. the SSH endpoint) and `publicDomain`. Each of those sections is derived only from what the platform actually exposes and is **omitted when it has nothing to say** — no readable quota, no `/proc`, no `/proc/net/tcp{,6}`, no `RAILWAY_*` — so a non-Railway container, a plain host, or macOS simply gets a shorter snapshot instead of placeholder fields or the host's numbers relabelled. Single compact JSON shape (no detail levels); tool probes are cached 5 min. OpenCode 2 registers tools from **plugins**, not from a `tools/` directory (a file there is never read — verified against 2.1.4), so the `.ts` is a `Plugin.define` + `ctx.tool.transform` registration and the dependency-free lib holds the logic and also runs directly (`node lib/sysinfo.ts`). The `lib/` tree is **TypeScript run by Node's own type stripping** (Node ≥ 24, no build step, nothing non-erasable such as `enum`/`namespace`/parameter properties), which is why the plugins import it with an explicit `.ts` extension — Node's stripping resolves the literal specifier, so `../../lib/x.js` would not find `x.ts`. Reads only whitelisted non-sensitive values.

## Railway networking

One service exposes one public port (`$PORT`, used by SSH). To reach the OpenChamber web UI (3001), add a **second public port** in Railway → Service → Settings → Networking → TCP proxy, mapped to container port `3001`. Then OpenChamber is at `https://<second-domain>.up.railway.app` (UI password from `OPENCHAMBER_UI_PASSWORD`, default `qingying`). The embedded opencode server (4096) stays on `127.0.0.1` and is proxied through OpenChamber — do not expose it directly.
