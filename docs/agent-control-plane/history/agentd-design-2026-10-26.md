# agentd — control plane for unattended OpenCode work

Status: **superseded, kept for history.** Moved here from `joops/feishu-bot/docs/` on 2026-10-28. The
canonical design is [`../design.md`](../design.md) — same decisions, plus the prior-art review, capability
model, experience base, delegation and recall. Do not edit this file; change the canonical document.

Revisions: 2026-10-26 — one agent per job; the reviewer session was dropped (§6.4), classification is rules
(§6.1), and "done" is artifact checks (§6.3). Same day: §1.1/§1.2 record which prior-art mechanisms are
compensations for weak models (removed) and which are accountability (kept); §18 capability model and tool
surface, §19 experience base, §20 delegation.

Scope: a long-running process that turns external requests (a Feishu message, a schedule, a webhook) into
**jobs**, executes them in OpenCode sessions, keeps state across restarts, gates dangerous actions on a
human, and reports back. Non-goals for P0: web UI, multi-tenant, Slack, CI-triggered runs, cross-repo
orchestration, a second agent runtime.

## 1. Decision summary

| Concern | Decision | Why |
| --- | --- | --- |
| Who owns job state, budgets, retries, approvals, dedupe | **Code** (this process) | These must hold even when a model is wrong or absent. A model that grades its own completion is not an acceptance check. |
| Who investigates, plans, codes, explains | **Model**, in an OpenCode session | There is no rule for "which log line matters". |
| What runs the agent loop | **OpenCode**, reused as-is | It already owns context compaction, skills/`AGENTS.md` resolution, MCP, permissions, worktrees, session persistence and an event stream. Rebuilding that is not product work. |
| How many agents | **Exactly one**: the execution session. No manager, planner or reviewer agent. | One agent keeps cost and failure modes countable; the loop is code, so it does not need a brain. |
| How a request becomes a job kind | **Rules** (trigger grammar, §6.1), default to "ask a human" | Deterministic, testable, no extra model call. |
| How "done" is decided | **Artifacts**, checked in code (§6.3) | PR open, CI green, diff in scope, tests ran. A session's own prose is data, not a verdict. |
| What the loop writes down | One contract: **brief** (in) | The session never gets to redefine what success means. |
| How a new capability is added | **Skill first**, tool only when a capability is missing, control-plane change last | Most additions are procedure, not code; the ladder is in §18.5 |
| Where hard-won experience lives | A searchable corpus on disk, **never auto-injected** (§19) | Too large, too stale, and writable by agents — it is reference material, not context |

Rejected: a self-built harness (Vercel AI SDK / pi-style framework) — it costs months rebuilding
`read → compact → tools → retry → permissions → worktree → persistence` and buys nothing this product needs;
a "manager agent" that owns the loop — state then lives in a context window, so it drifts under compaction,
duplicates work on redelivery, cannot be tested, and forgets boundaries as context grows. A second
(reviewer) agent was also considered and deferred: artifact checks cover the measurable half of "done" at
zero token cost, and one agent keeps the system explainable. §15 records when that decision should be
revisited.

### 1.1 Compensations for weak models — removed

Every project in this space was designed when a model could not hold a task, so its architecture
compensates with process. That compensation is paid per turn, forever; with current models it costs more
than it buys. What we removed, and what it was paying for:

| Mechanism | Where it comes from | What it compensated | What we do instead |
| --- | --- | --- | --- |
| finite run per turn, context rebuilt from the database | paperclip (`doc/architecture/durable-continuation-scheduler.md`: "does not keep an agent process alive between turns") | a model that forgets between turns and a context window that cannot hold the job | one long session per job; OpenCode compacts; a new session only for a new job or after a hard failure, with a five-line handoff |
| issue → sub-issue decomposition | paperclip (`doc/TASKS.md`: Workspace → Initiatives → Projects → Milestones → Issues → Sub-issues) | a single run could not carry a deliverable | one job = one acceptance-checkable unit, described in one brief |
| orchestrator / worker / reviewer roles | agent-orchestrator (`SessionKind` = `worker` \| `orchestrator`, `reviewerharness.go`) | a model that could neither plan nor check itself | one agent + artifact checks; the human is the reviewer |
| per-turn stop gates | hermes (`agent/turn_stop_gates.py`: four gates append the answer as interim and continue the turn) | a model that declares victory early | one gate per delivery (CI + PR), plus a plan gate before code |
| consensus / voting verification | ruflo (queen-led swarm, consensus protocols) | a single model that cannot be trusted | one strong model + deterministic checks; voting only helps with independent errors, and same-family errors correlate |
| a 300+ tool catalogue | ruflo (~339 tool source files; tens of thousands of tokens of schema before any work starts) | a model that cannot find the right capability | ≤ 20 tools per job kind; procedures live in skills, not in tool names |
| large RAG / full-text memory | openclaw, hermes (FTS5 session search) | a context window too small to hold the repository | the repository is the context (`AGENTS.md`, skills, codegraph); notes only across jobs |
| fresh-session handoff as the normal path | paperclip's OpenCode adapter (`hydrateFreshSessionHandoff`) | sessions that could not be resumed reliably | handoff is an exception after failure, not the turn boundary |

What this is not: optimism about models. We move the trust from *process* to *artifacts* — the checks in
§6.3 are what makes dropping the scaffolding safe. One mechanism stays for a non-model reason: **turn
admission** (one turn per session at a time) is concurrency control, not a capability patch.

### 1.2 Responsibilities that stay

Three things are about accountability, not capability. A stronger model makes each more important: failures
become rarer and more expensive, and a plausible wrong answer is harder to spot.

1. **Artifact acceptance.** PR open, CI green, diff in scope, acceptance checks run. The executor is the
   only participant that knows what it ran — which is also why it is the participant most likely to call it
   done. A machine check is the only claim that survives a restart, a compaction, or a reviewer who was not
   there. Shape: `acceptance[]` with deterministic checks (`pr.open`, `ci.green`, `tests_passed:<cmd>`,
   `file.non_empty:<path>`, `diff.within:<paths>`); anything that cannot be evaluated deterministically is
   `UNVERIFIED` and goes to a human. (Borrowed from deer-flow's `acceptance_criteria` plus execution
   receipts.)
2. **Write-path boundaries.** Worktree isolation, branch rules, a per-job permission profile, approvals with
   default-reject and a timeout. A stronger model spends less time being wrong and more time being
   confidently wrong at scale; one helpful extra command can merge or deploy. Permission rules are the only
   boundary the model cannot argue with (§7).
3. **Recovery, idempotency, budget, audit.** A job row, one idempotency key per trigger, reconciliation on
   start and on reconnect (the event stream has no replay), a spend ceiling with a hard stop, an append-only
   event log. Unattended means nobody is watching: every silent failure must become a visible state, and
   every redelivery must be unable to create a second job.

**Where the gate goes.** Because checks moved from per-turn to per-delivery, the human gate moves earlier:
approving a plan costs a minute and catches the expensive mistake; reviewing a 400-line diff costs half an
hour and catches the cheap one. Corollary: a job that cannot state its plan in five lines is not ready to
run.

**What we would add back.** If a class of work starts passing its checks while being wrong — copy changes,
design judgement — add a second session for that class only (§15). Not for everything.


## 2. Two loops, one agent

```
trigger ─▶ rules: which kind ─▶ create job ─▶ state machine ─▶ run session ─▶ wait events
                                                                     │              │
                                                              one agent        code: check artifacts
                                                              (session)        PR / CI / diff / tests
                                                                     │              │
                                                                     └──▶ notify ◀──┘
   ▲
   └── Feishu (P0) · cron (P1) · HTTP webhook (reserved) · Slack (reserved)
```

The outer loop is roughly 2–3k lines. Anything it cannot decide becomes `blocked` with a question, not a
guess. There is exactly one agent per job, and it is always the execution session — nothing supervises
another model.

## 4. Data model

SQLite (WAL) via `node:sqlite`, in the shared state directory (`state.ts`), never inside a checkout. Jobs
are the unit humans care about; sessions are workers and are not duplicated here.

```sql
create table jobs (
  id             text primary key,              -- ulid
  kind           text not null,                 -- qa | fix | requirement | incident | maintenance
  intent         text not null,                 -- the request, verbatim
  status         text not null,                 -- queued|running|waiting_human|waiting_ci|blocked|done|failed|cancelled
  project_id     text,
  directory      text,                          -- session location
  worktree       text,                          -- null for read-only jobs
  branch         text,
  base_sha       text,                          -- origin/main at dispatch time
  channel        text,                          -- "feishu:oc_xxx:omt_yyy"
  idempotency    text not null unique,          -- channel message id / trigger id
  budget_tokens  integer,
  cost_usd       real not null default 0,
  session_ids    text not null default '[]',    -- JSON array; a job may use several sessions
  result         text,                          -- JSON: {pr, answer, diffStat, report, checks}
  attempts       integer not null default 0,
  last_event_at  integer,
  created_at     integer not null,
  updated_at     integer not null
);
create index jobs_status on jobs(status, created_at);
create index jobs_channel on jobs(channel);

create table job_events (                        -- audit + forensics; never deleted
  job_id text not null, seq integer not null, at integer not null,
  type text not null, payload text,
  primary key (job_id, seq)
);

create table approvals (
  id text primary key, job_id text not null, session_id text not null, request_id text not null,
  action text not null, resources text, message text,
  status text not null,                          -- pending|once|rejected|timeout
  asked_at integer not null, decided_at integer, decided_by text
);
create index approvals_pending on approvals(status);

create table sessions_seen (                     -- one row per session this process created
  session_id text primary key, job_id text not null, created_at integer not null, removed_at integer
);
```

Why no `sessions` mirror: OpenCode is the source of truth for session state. We keep the id list so a
restart can reconcile; everything else is fetched (`session.get`). `session.list` filters by directory, not
by metadata, so the store must own the ids.

## 5. Job lifecycle

```
queued ──dispatch──▶ running ──artifacts ok──▶ done
   │                   │  ▲
   │                   │  └──human answered──▶ running
   │                   ├──permission.asked──▶ waiting_human
   │                   ├──PR opened─────────▶ waiting_ci ──CI green──▶ done
   │                   ├──no progress 15m───▶ blocked
   │                   └──budget exhausted──▶ failed(budget)
   └──cancelled
```

Transitions are written as code, one function per edge, each appending a `job_events` row. Rules that
matter more than elegance:

- **No state without evidence.** `done` requires artifact checks (§6.3) — or, for `qa`, a non-empty answer the
  thread actually received. `waiting_ci` requires a PR URL.
- **Stall detection.** 15 minutes without any session event for a running job triggers `session.get`; if not running and no artifacts, `blocked`.
- **Only two automatic retries.** Then `failed`, keeping worktree and branch for a human to take over.
- **Unknown request shapes go to a human**, not to a fallback workflow. This is what keeps the rule count bounded (~8 states, ~12 transitions).

## 6. Job contract: one agent

Every job creates exactly one session and nothing else runs a model. Verified client surface (v2):

```ts
const session = await client.session.create({
  title: `[${job.kind}] ${title}`,                       // human-findable in any UI
  location: { directory: job.worktree ?? job.directory },
  metadata: { jobID: job.id, kind: job.kind, channel: job.channel, baseSha: job.baseSha },
  permissions: profileFor(job.kind),                      // appended after agent rules
});
await client.session.switchAgent({ sessionID: session.id, agent: agentFor(job.kind) });
await client.session.prompt({ sessionID: session.id, text: brief(job), delivery: "queue" });
```

`delivery: "queue"` always: `steer` (the default) interrupts whatever the session is doing, which is never
what a control plane wants.

**6.1 Which kind of job — rules, no model.** A prefix or a thread with a known context decides; anything
unrecognised asks instead of guessing:

| Input | Kind |
| --- | --- |
| a message in a report's topic, or `/ask …` | `qa` |
| `/fix …`, or a message that matches a printed "fix" phrase | `fix` |
| `/req …`, or a message that matches a printed "requirement" phrase | `requirement` |
| `/status`, `/cancel <id>` | control command, no job |
| anything else | reply with three choices (问答 / 修复 / 需求); 30 min without an answer → drop |

The phrase list lives in `rules.ts` as data, one line and one test per phrase. It stays small on purpose: the
default path is one question to the human, which is cheaper and more honest than a keyword soup that
occasionally starts a 40-minute coding job for a question.

**6.2 The brief — intent, never the security boundary.** Full session with skills, tools and the profile in
§7:

```
[任务] <one-sentence goal>
[范围] only <worktree>; base origin/main@<sha>
[边界] no merge, no deploy, no production writes; read-only queries via <how>
[完成标准] <test command>; produce <PR url | answer>
[预算] <tokens>; stop and report if exceeded
[汇报] ≤5 lines: what changed, how it was verified, what is left
```

**6.3 "Done" is decided by artifacts, in code.** The session's prose is stored for humans (`result.report`)
and is *not* the transition condition:

| Job kind | Checks that must all pass |
| --- | --- |
| `fix` / `requirement` | branch exists and is not the default branch; PR is open for that branch; CI on the PR head is green; diff is non-empty and touches no path outside the repo; the quoted test command appears in the session's report |
| `qa` | a non-empty answer, delivered (message id returned by the channel), nothing else |
| `incident` / `maintenance` | the report exists and every claim in it cites a query or a log window the job actually ran |

Concrete shape — one list per job, evaluated in code, never by prose:

```jsonc
"acceptance": [
  { "check": "pr.open",        "branch": "agent/<slug>" },
  { "check": "ci.green" },
  { "check": "tests_passed",   "command": "cd vercel && pnpm check" },
  { "check": "file.non_empty", "path": "vercel/src/**/fix*.ts" },
  { "check": "diff.within",    "paths": ["vercel/", "core/"] }
]
```

A check that cannot be evaluated deterministically is stored as `UNVERIFIED` and routed to a human; it never
counts as done. CI is the evidence of correctness: it runs the project's own checks on the real diff, which
is stronger than asking a second model to re-read the diff and guess.

**6.4 Why there is no reviewer session.** A fresh session has no memory of what was attempted, so it
re-derives the problem and can be confidently wrong about a change the executor verified; and the executor is
the only participant that knows what it ran. Objectivity is therefore bought from machine-checkable
artifacts (CI, PR state, diff scope) rather than from a second opinion. §15 records the case that would
reopen this: work whose correctness cannot be expressed as a check.

## 7. Permissions

Verified defaults (OpenCode v2): every agent starts with `{action:"*", resource:"*", effect:"allow"}` plus
`.env` reads → `ask`; **the last matching rule wins**; any `deny` among multiple resources denies; session
rules are evaluated after agent rules; saved approvals are durable project-scoped `allow` and never override
a `deny`. So "auto-approve everything except sensitive things" is already the default — the work is the
sensitive list, not an approval switch.

Profiles are appended per job kind (`perms.ts`). Baseline for `fix` / `requirement`:

```jsonc
[
  { "action": "read",  "resource": "*.env",  "effect": "deny" },
  { "action": "read",  "resource": "*.pem",  "effect": "deny" },
  { "action": "shell", "resource": "*",      "effect": "ask" },     // intent: explicit shell allow-list below
  { "action": "shell", "resource": "git status *",   "effect": "allow" },
  { "action": "shell", "resource": "git diff *",     "effect": "allow" },
  { "action": "shell", "resource": "git add *",      "effect": "allow" },
  { "action": "shell", "resource": "git commit *",   "effect": "allow" },
  { "action": "shell", "resource": "git push origin HEAD*", "effect": "allow" },
  { "action": "shell", "resource": "git push origin main*", "effect": "deny" },
  { "action": "shell", "resource": "git push * --force*",   "effect": "deny" },
  { "action": "shell", "resource": "gh pr merge*",   "effect": "deny" },
  { "action": "shell", "resource": "gh pr create*",  "effect": "allow" },
  { "action": "shell", "resource": "*deploy*",       "effect": "deny" },
  { "action": "shell", "resource": "*railway up*",   "effect": "deny" },
  { "action": "shell", "resource": "vercel --prod*", "effect": "deny" },
  { "action": "shell", "resource": "*migrate*",      "effect": "deny" },
  { "action": "shell", "resource": "rm -rf *",       "effect": "deny" },
  { "action": "external_directory", "resource": "*", "effect": "deny" },
  { "action": "question", "resource": "*", "effect": "allow" }
]
```

Q&A profile: no `edit`, no `git push`, shell narrowed to read-only prefixes (`ls`, `cat`, `tail`, `jq`,
`git log`, `git show`, `curl` to allow-listed hosts), no production credentials in the process environment.

Two facts that shape this section:

1. **Shell matching is best effort.** Official docs warn that directory inference from command text is
   heuristic and advise a narrow allow-list over patterns meant to catch every dangerous command. Deny rules
   are layer two; they are not the wall.
2. **`allow always` writes a durable rule.** The control plane answers `permission.asked` with `once` only;
   widening is a reviewed config change. Otherwise rules accumulate and nobody can explain them.

Layer one is therefore the environment: the job's process has no production write credential, and the
worktree is the only writable place. Layer three is audit (`approvals` + `job_events`).

Approval routing: `permission.asked` carries `{id, sessionID, action, resources, save, message}`. Render one
message with the exact command and three choices (`1 once / 2 reject / 3 never`), timeout 30 min → `reject`,
never auto-approve. Who may approve is an `open_id` allow-list (the contact scope is not granted, so
usernames are not available from the API).

## 8. Worktrees

- `git fetch origin` in the canonical checkout, then `worktree.create({ projectID, name: slug, branch: "agent/<slug>" })`.
- **Verify the base**: `git -C <dir> rev-parse HEAD` must equal the recorded `origin/main` sha, else fail the job. The exact semantics of the API's `branch` field are *not yet verified* (see §15).
- One active session per worktree, enforced by the store.
- Cleanup: `done` + merged → remove; `failed` → keep for 7 days (a human may want the diff), then a nightly sweep removes it. Never remove a worktree with uncommitted changes without `force`.

## 9. Events and reconciliation

`client.event.subscribe()`; keep `(sessionID, event.id)` for dedupe. Relevant events:

| Event | Use |
| --- | --- |
| `session.execution.started` | running, refresh `last_event_at` |
| `session.execution.succeeded` / `session.idle` | candidate completion → run artifact checks (§6.3) |
| `session.execution.failed` | carries `error` → classify (transient vs human) |
| `permission.asked` | approval routing |
| `session.created` / `deleted` / `forked` | repair session bookkeeping |
| `worktree.updated` | detect a worktree removed behind our back |

The stream is **live-only (no replay)**. So reconciliation is part of the main loop, not a startup step:

1. On start and after every reconnect: read `jobs` in `running|waiting_human|waiting_ci`.
2. `session.get` each id: idle → run artifact checks and finish; still running → re-attach; 404 → `failed(session removed)`.
3. Re-send pending approvals, marked as "from before the restart".
4. Persist every event before acting on it.

## 10. Concurrency, queue, budget

- Global concurrency 3 (config), per project 2, one session per worktree.
- Queue = `jobs where status='queued' order by created_at`; no external broker.
- Budget: sum `cost`/tokens from `session.get` after each transition. 80% → notify, 100% → `session.interrupt` and `failed(budget)`.
- Per-job cost is recorded so a daily report can answer "what did the agent spend".

## 11. Notifications

- Only on state transitions; never per event.
- Dedupe key `jobID + status + hash(result)`, suppressed for 24 h.
- Failures go to an outbox with exponential backoff (3 attempts), then a loud log line.
- Every notification answers: what is this, what state, **what happens next and who must act**, link.

## 12. Observability

```

```

## 13. Failure taxonomy

| Class | Example | Action |
| --- | --- | --- |
| transient | 429, network, provider 5xx | one retry with backoff |
| underspecified | "修一下" without a subject | `blocked`, ask one question |
| permission / approval | deny or approval timeout | `blocked`, never auto-retry |
| bad output | tests red, no PR | one more execution round (max 2), then `failed` |
| budget | tokens exhausted | stop immediately, keep evidence |
| infrastructure | OpenCode unreachable | keep job `queued`, retry with backoff, notify if > 10 min |

## 14. Channel adapter (reserved integration surface)

```ts
export interface InboundEvent {
  channel: string;                 // "feishu:oc_xxx:omt_yyy"
  externalId: string;              // message id — the idempotency key
  text: string;
  author: { id: string; name?: string };
  thread?: string;
}

export interface ChannelAdapter {
  start(onEvent: (event: InboundEvent) => Promise<void>): Promise<void>;
  stop(): Promise<void>;
  reply(ref: string, markdown: string): Promise<void>;          // answer in the same thread
  askApproval(ref: string, ask: ApprovalAsk): Promise<string>;  // returns approval id
  notify(ref: string, message: NotifyMessage): Promise<void>;
}
```

Feishu implements it in P0 by wrapping the existing bridge (whitelist, seen-set, outbox, single consumer).
Slack and an HTTP adapter are stubs that throw `not implemented`; adding them must not touch the loop.

## 16. Milestones and acceptance

**P0 — unattended Q&A (~1 week).** Feishu message → job → read-only session → answer in the thread; restart
reconciles; `GET /status` shows it. Acceptance: kill -9 the process mid-job, restart, the job finishes and
answers exactly once.

**P1 — fixes and requirements (~2 weeks).** Worktree from `origin/main`, one session implements and verifies, PR,
CI loop, two human gates (plan approval, merge). "Done" is the artifact check of §6.3, not the session's
self-report. Acceptance: one sentence in Feishu produces an open PR whose CI is green; pushing to `main`
from the session is denied and logged; an approval timeout rejects; a job whose CI stays red ends `failed`
with the branch kept.

**P2 — breadth.** Plugin for prompt metadata (replacing the `[feishu:group/person]` text prefix) and
permission defaults; MCP facade (`job.create|list|get|cancel`, `session.tail`); Slack; cron jobs; a nightly
briefing built on `system-inspection`.

## 18. Capability model and tool surface

### 18.1 Six axes, not a tool list

A tool list answers "what can it call". The thing being built is a delegate, so the useful question is what
a colleague needs to be useful. Six axes, and who supplies each:

| Axis | What it means | Supplied by | This project adds |
| --- | --- | --- | --- |
| Perception | read the repo, its history, runtime logs, metrics, outside docs | OpenCode `read`/`grep`/`glob`/`shell`/`webfetch`, codegraph | `logs.*`, `metrics`, `research.ask` |
| Action | change code, run checks, open a PR, message people | OpenCode `edit`/`write`/`patch`/`shell`, `gh` via shell | `pr.*`, `channel.send`, `acceptance.check` |
| Memory | what happened, what was decided, what hurt last time | session + compaction; `jobs`/`job_events` (§4) | the experience corpus (§19) |
| Judgement | when to do which thing, in what order, to what standard | skills and `AGENTS.md` | trigger rules (§6.1) and the brief (§6.2) |
| Boundaries | what may be touched, by whom, for how long | permissions (§7), worktrees (§8) | delegation scopes (§20) |
| Feedback | is it actually finished | event stream, CI | acceptance checks (§6.3), approvals |

Capability and authorization are different things. Capability is which tools exist; authorization is what
this job, for this person, in this environment may do with them. Neither implies the other, and conflating
them is how "the agent can do everything I can" becomes an incident.

### 18.2 Principles

1. **Tool count is a context tax.** A tool's name, description and schema cost roughly 40–120 tokens; a
   300-tool catalogue is ~18k tokens before any work starts, and near-duplicate names add selection noise.
   Budget: **≤ 20 tools visible per job kind**.
2. **A tool returns evidence, not prose.** A message id, a PR URL, a log count with an exemplar, an exit
   code. Anything else is a claim that has to be re-checked by a human.
3. **Procedures do not belong in tools.** A tool answers "do X once"; a skill answers "when, why and in what
   order". Most capability requests should end as a skill, not as code.
4. **Progressive disclosure.** The skill names the tool; the tool is one call away. No tool catalogue, no
   search-the-registry meta-tool, no "maybe this tool helps" exploration.
5. **Reversible by default.** Branch before push, PR before merge, dry-run before write, read-only query
   before anything else. Irreversible actions are a human's job (§20).
6. **No tool widens its own authority.** Approvals are `once`, never `always`; an elevated scope expires
   with the job; a tool cannot grant itself a permission.
7. **If three lines of shell under the existing profile can do it, do not build the tool.** Build it when
   structured output, a permission boundary, or repeatable cost matters — not because it feels tidier.

### 18.3 The surface

P0 is what the first two job kinds need. Nothing here duplicates a built-in.

| Tool | Job kinds | Purpose | Returns | Permission action |
| --- | --- | --- | --- | --- |
| `logs.dump` | qa, fix, incident | fetch one window into a local NDJSON store (Vercel, Railway) | row count, window, path | `logs_dump` |
| `logs.query` | qa, fix, incident | group/filter/sample the dump by path, level, status, client | counts + up to N exemplars | `logs_query` |
| `metrics` | qa, incident, maintenance | DB/LangSmith/Vercel/GitHub aggregates behind the read-only SQL guard | numbers with the window they cover | `metrics` |
| `experience.search` | all | find prior lessons by symptom and tags | ≤ 5 hits: title, one line, path, status, date | `experience_search` |
| `experience.write` | all | draft a lesson after a non-obvious fix | draft path, never `confirmed` | `experience_write` |
| `acceptance.check` | fix, requirement | run this job's acceptance list before claiming done | per-check pass / fail / `UNVERIFIED` | `acceptance_check` |
| `channel.send` | maintenance, requirement | post or update a message/card in a whitelisted chat | message id | `channel_send` |

P1: `pr.open` / `pr.status` (structured PR state instead of parsing `gh` output; `pr_open`, `pr_status`),
`deploy.status` (current deployment plus recent failures; `deploy_status`), `research.ask` (external repo or
doc question with citations; `research_ask`).

P2, only when a concrete need shows up: `sandbox.exec` (disposable container; `sandbox_exec`),
`budget.status` (`budget_status`), `incident.open` (`incident_open`).

Count for the heaviest P0 kind (`fix`): 8 built-ins that matter (`read`, `glob`, `grep`, `edit`, `write`,
`patch`, `shell`, `webfetch`) + `logs.dump`, `logs.query`, `metrics`, `experience.search`,
`experience.write`, `acceptance.check`, `todo`, `question` = **16**. Adding P1's two PR tools keeps it at 18.

### 18.4 Deliberately not exposed

- Raw SQL. Only the canned aggregates behind `metrics`; the guard is enforcement, not advice.
- Production write APIs: deploy, migrate, billing, credit spend, account provisioning.
- Secret stores (Doppler, Vercel env, Railway variables).
- A general-purpose tool catalogue, or a meta-tool that lists tools.
- Arbitrary HTTP to internal admin endpoints.
- `edit` outside the job's worktree; `external_directory` is denied (§7).

### 18.5 The customization ladder

| Level | You add | Code change | Review | Example |
| --- | --- | --- | --- | --- |
| 1 | one line of preference or boundary in `AGENTS.md` | no | none | "never touch billing code" |
| 2 | a skill (`SKILL.md` + references) | no | none | how to triage a 5xx |
| 3 | a tool: an MCP server or a thin tool in this repo | yes | yes | a new log source |
| 4 | control-plane behaviour: a job kind, state, acceptance rule | yes | yes + migration | scheduled audits |

Two rules keep the ladder honest. A new capability **must not require touching the state machine**; if it
does, it is level 4 and needs a design note. And a level-2 addition **must declare its acceptance checks**,
otherwise jobs it creates can never legitimately end as `done`.

## 19. Experience base

### 19.1 Never auto-loaded

Hard-won lessons are the most valuable thing a long-running delegate accumulates, and the worst thing to
inject on every turn. Three reasons it is a corpus to query, not context to load:

- **Size**: a year of incidents is hundreds of kilobytes; the top few notes are never the ones needed.
- **Staleness**: advice correct for Next 15 or a retired provider is actively misleading later.
- **Injection**: agents write these notes, and notes are text; anything injected wholesale is a channel for
  "ignore your instructions". Treat the corpus as untrusted input.

So: no note goes into a system prompt, ever. Retrieval is a tool call (§18.3), and the retrieved text is
quoted as reference material.

### 19.2 Lifecycle

```
capture → review → index → retrieve → expire / supersede
```

A note is `draft` on write. It becomes `confirmed` only when a human says the fix held, or a later job cites
it successfully. Nothing is promoted automatically — most days produce zero notes, and that is the correct
outcome.

### 19.3 Shape

One file per lesson: `experience/<yyyy-mm-dd>-<slug>.md`, front matter plus a short body.

```markdown
---
id: 2026-10-23-mcp-subscriptions-timeout
title: MCP subscriptions/listen hits the 60 s function limit
symptom: /api/mcp 504 roughly every 61 s, 400+ error rows per day
root_cause: the SDK serves subscriptions over SSE; maxDuration is 60 s
fix: reject subscriptions/listen on the stateless endpoint (PR #1484)
verify: error rows for that route fall to zero in the next window
tags: [mcp, vercel, timeout]
evidence:
  - log window 2026-10-23T00:00/13:49, 379 rows
  - pr:1484
status: confirmed
review_after: 2027-04-23
---

What we saw, what we tried that did not work, and the check that would catch a regression.
```

`evidence` needs at least one verifiable anchor: a log window, a command with its exit code, a PR/commit, or
a dashboard link. A note without evidence is a rumour.

### 19.4 Retrieval

Two stages, cheap then precise:

1. `experience.search("mcp 504 every minute")` matches title/symptom/tags and returns ≤ 5 hits with a
   one-line summary, status and date.
2. The session reads **at most three** full notes.

Index size is roughly 60 bytes per hit, so even a 500-note corpus costs a few kilobytes *only when a task
asks for the whole index* — which nothing does. Add embeddings only past ~500 notes or when keyword search
demonstrably misses; until then a filename/tag/title index is smaller and more predictable.

### 19.5 Governance

- **Untrusted text.** When a note enters a prompt it is wrapped as `<experience source="...">` and labelled
  reference material, not instructions.
- **No auto-promotion** to `confirmed`; a human or a successful later citation does that.
- **Contradiction is explicit.** A new note sets `supersedes:` and the old one becomes `superseded`; both
  stay searchable so a stale recommendation is visible as stale.
- **Expiry.** `review_after` defaults to six months; expired notes are marked `stale` and ranked lower.
- **Dedupe** by content hash of symptom + root cause, so re-diagnosing the same failure updates one note.
- **No secrets, tokens or customer data** in a note — it is a document in a repository.

### 19.6 Capture

- **Explicit**: after a fix whose cause was not obvious, the session may call `experience.write` with a
  draft. It is a level-2 action: no code, no new tool.
- **Nightly distillation**: the control plane reads the day's `job_events`, drafts 0–3 candidate notes and
  offers them in the channel for one-tap approval. Rejection is the default for a normal week.
- **Never** from an unfinished job: a note written before the fix is verified is exactly the stale advice
  that makes the corpus useless.

## 20. Delegation: authorization, not capability

The target is not "it can do everything I can". It is "it can do everything I delegated, with the same audit
trail as if I had done it". Authorization is granted per scope; capability (§18) is what the tools allow.

| Dimension | Rule |
| --- | --- |
| Identity | One bot identity per environment (dev, prod). Never a person's token, never a shared human account. |
| Scope | (person, channel) → allowed job kinds; (job kind) → tool profile + acceptance list; (environment) → read or write. |
| Time | Approvals are `once`; an elevated grant expires when the job ends. Nothing is remembered as "always allowed". |
| Reversibility | Default path is branch → PR. Merge, deploy, migrate, spend, and anything sent under a human's name require a human. |
| Audit | Every tool call and every approval lands in `job_events`; a job's report must cite the evidence it relies on. |
| Blast radius | Worktree only, `external_directory` denied, no production write credentials in the session environment. |
| Revocation | Removing a person from the chat allow-list (`src/whitelist.ts`) stops new jobs from them immediately; running jobs are cancelled with `job.cancel`, not left to finish. |
