# 游戏里内置模型 vs 接外部大模型 API

**问题：** 单人 Godot 游戏（¥30、殖民地/建造类）能不能内置本地模型，或接外部 LLM API？
**日期：** 2026-11-02

## 结论

**能，但对这个项目，最优解是第三条：构建期预生成。**

| 方案 | 运行时成本 | 延迟 | 包体 | 合规负担 | 推荐度 |
|---|---|---|---|---|---|
| **A. 构建期预生成** | $0 | 0 | +几 MB JSON | 只要“预生成”披露 | **★★★★★ 默认** |
| B. 内置本地小模型 | $0 | 0.5–5 秒 | +0.5–3 GB | 现场生成：护栏 + 举报入口 | ★★★ 可选功能 |
| C. 外部 API | 按调用付费 | 0.5–3 秒 | 0 | 现场生成 + 付费方式问题 | ★ 不做 |

## 一、方案 C 的真正门槛不是技术，是 Valve 的付费规则

技术上最简单：`HTTPRequest` + 一句 prompt，20 行代码。

但 Valve 的内容调查 FAQ 写得很清楚 [S1]：

> “如果你的游戏连接一个按每次输入/输出计费的实时生成 AI 服务，你需要代表玩家管理对该外部服务的访问，并用 Steam 支持的支付方式向玩家收费。”

它给出四种做法：把成本算进游戏售价、按次微交易、订阅、或一次性 DLC 解锁。

对一款 ¥30 的游戏，这意味着：

- **你自己出 key**：要么涨价覆盖成本（不可控，人均调用量差异极大），要么做微交易（对一个 ¥30 买断制游戏是体验灾难）；
- **玩家自带 key（BYOK）**：合规上最干净，但要求玩家去注册 OpenAI/DeepSeek、充值、填 key——99% 的玩家不会做；
- **代理服务器**：你得自己运维、限流、防滥用，还要处理 key 泄露与账单爆炸。

成本量级：每局 100 次调用 × 300 token ≈ 3 万 token；按小模型 $0.6/M 输出计约 **$0.02/局**。5,000 份 × 10 局 = **$1,000–2,000**。金额不算大，但它是**持续支出 + 运维 + 合规**三件事叠加，对单人项目是负担。

## 二、方案 B：本地模型已经可用，但要看你在游戏里让它干什么

Godot 侧已有成熟方案：

| 方案 | 特点 |
|---|---|
| **Godot Llama**（Asset Library, MIT, 2026-02） | 官方资产库，`LlamaModel/Context/Sampler`，流式生成、取消、KV 缓存存取 [S2] |
| **GDLlama**（GDExtension, 4.4+） | 支持 JSON schema / GBNF 语法约束、函数调用、embeddings [S3] |
| **Chorus-LLM**（Asset Store, 2026-10） | 专为游戏设计：**多 NPC 共享一个模型**、优先级调度、连续批处理；实测 40+ NPC 同时对话 [S4] |

关键能力是**语法约束输出**（GBNF / JSON schema）：让模型只能吐合法的结构化结果，这样它就不可能“把游戏搞坏”。

现实约束：

- **模型大小**：0.6B ≈ 0.4 GB、1–1.7B ≈ 0.8–1.2 GB、3–4B ≈ 2–2.5 GB（Q4 量化）。包体直接翻倍，下载转化率会掉。
- **速度**：桌面 CPU 上 1B 约 30–60 tok/s、3B 约 10–20 tok/s；低端笔记本更慢。本容器实测：1.7B 在 **8 线程下约 0.5 秒**生成一段短文本，而按 `nproc` 报的 48 线程跑要 **37 秒**（超订 6 倍）——说明“线程数按 cgroup/物理核配”这件事在发布版里也必须做对。
- **Steam Deck**：4 核 Zen2，跑 1B 勉强、3B 不可用。如果要 Deck Verified，本地模型只能做成可关闭的附加功能。
- **合规**：本地生成仍属 Steam 的 **Live-Generated**，需要申报护栏、并在游戏内提供举报入口 [S1][S5]。

## 三、方案 A：为什么它才是默认答案

把“生成”挪到构建期：

- 用 API 离线批量生成 **5,000–10,000 条**文本（殖民者台词、事件描述、编年史、物品风味文本、名字库），存成 JSON 随游戏发布；
- 运行时只做检索与拼接（按状态、性格、事件类型打标签）；
- 成本一次性 **$20–200**，无延迟、无网络、无 key、无运维；
- Steam 归类为 **Pre-Generated**，只需常规披露，不需要护栏与举报通道；
- 玩家断网、Deck、低端机全部可用。

对殖民地/建造类，这覆盖了 95% 的“想要 AI 味道”的需求：**玩家感受到的是“文本很丰富”，而不是“它在实时思考”。**

## 四、什么情况下才值得上运行时生成

只有当“AI 是卖点”本身时：

1. **自由对话 NPC**（玩家可以问任何问题）——这是唯一本地/外部模型不可替代的场景；
2. **无限内容的 roguelike 事件**——但预生成 1 万条 + 组合规则通常够用；
3. **玩家自建 mod/剧本的实时翻译或改写**。

即便如此，也要遵守三条工程纪律：

- **模型只产出“文本/结构化建议”，不产出“游戏状态”**：数值、胜负、存档一律由确定性代码决定；
- **语法约束输出**：JSON schema / GBNF，解析失败就回退到模板文案；
- **超时与降级**：800 ms 没出结果就用预生成文案，绝不让玩家等。

## 五、给这个项目的具体建议

1. **v1 不做运行时生成。** 用构建期预生成做“编年史 + 台词 + 事件描述”，成本 $50 以内，风险为零。
2. **如果一定要有 AI 感**：做一个可选开关「本地编年史生成器」，1–1.7B 模型 + JSON 约束，默认关闭，独立 DLC 或免费附加包（避免主包体积翻倍）。
3. **不接外部 API**，除非改成 BYOK 并在设置里明确写“需要你自己的 API Key”。
4. **披露照实写**：预生成与现场生成在 Content Survey 里是两栏，别混。
