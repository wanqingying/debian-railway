# 方案选择：Jev 当老师 vs 内置决策小模型

**前提：** 派系领袖/首领的决策；单人 Godot 游戏；¥30；关键角色 3–5 个，决策频率每 30–60 秒一次。
**候选：** ① Jev 当老师（离线标注 → 蒸馏/编译）；② 内置 1.7B 小模型本地运行。
**日期：** 2026-11-02

## 结论

**选 ①，但不是“Jev 标注 → 训练小模型”，而是“Jev 标注 → 编译成策略表”。**

理由是你的那个直觉：**有限的是“决策相关状态”，不是“游戏状态”。** 领袖真正需要的输入只有 5–6 个维度：

| 维度 | 档位 | 例 |
|---|---|---|
| 经济 | 4（饥荒/紧张/稳定/富余） | 粮食天数、现金 |
| 军事 | 4（虚弱/均势/优势/压倒） | 兵员、装备 |
| 威胁 | 4（无/边境摩擦/集结/入侵中） | 邻居兵力、距离 |
| 机会 | 3（无/窗口期/真空） | 对手内乱、资源点空置 |
| 关系 | 3（敌对/中立/盟友） | 条约、历史恩怨 |
| 性格 | 3–5（好战/商人/偏执…） | 固定标签 |

5×4×4×3×3 ≈ **2,880 格**（乘性格最多 1.4 万格）。这就是“可以穷举”的真实规模——不是 10^30，而是几千。

**几千格意味着：不需要运行模型，只需要一张表。**

- Jev 标注成本：1.4 万格 × 约 1k token ≈ 1.4×10^7 token ≈ **$0.6**（$42/Btok），并行跑几十分钟；
- 表体积：1.4 万格 × 6 个意图 × 概率 ≈ **1–2 MB**；
- 运行时：**0 ms、0 成本、确定性、可存档、可 diff、可 mod**。

## 一、两个方案的正面对比

| 维度 | ① Jev 当老师 → 策略表 | ② 内置 1.7B 小模型 |
|---|---|---|
| 运行时成本 | **0** | 0（电费） |
| 单次决策延迟 | **< 1 ms**（查表） | 0.3–1 s（CPU）/ <0.2 s（独显） |
| 包体增加 | **1–2 MB** | **1.1 GB**（Q4） |
| 确定性/存档 | **完全确定** | 需缓存决策 |
| 质量上限 | 受抽象粒度限制 | 能处理表外状态 |
| 可解释性 | **可打印整张表、可手改** | 黑箱，只能看输出 |
| 硬件要求 | 无 | AVX2、8 线程舒适线；低端机 1–3 s |
| 工程风险 | 低（无平台二进制、无 GGUF/ONNX） | 中高（导出、readout、线程、驱动） |
| Steam 披露 | **Pre-Generated** | Live-Generated（护栏+举报入口） |
| 迭代成本 | 重跑标注（$1 级） | 重新微调 + 重新导出 + 重新测 |

**关键对比：你在方案 ② 里付出 1.1 GB 包体 + 平台适配 + Live-Generated 合规，换来的是 kenning-xl 在 agent 决策上 0.86 vs Jev 0.90 的 4 个点差距——而且是“更差”的 4 个点。**

## 二、为什么“表”反而比“模型”更像智能

1. **全局一致性**：模型逐格判断会有噪声（同一局面换个说法给不同答案）；表可以在生成后做单调性校验（“越富越不可能逃跑”），手动修正异常格。
2. **可调难度**：同一张表，按难度混合不同性格的表（70% 好战 + 30% 商人），比“让模型变笨”可控得多。
3. **可解释**：玩家问“它为什么打我”，你能查到格子编号；做 QA 时能直接看 CSV。
4. **可 mod**：表是数据，玩家和 mod 作者能改——这在殖民地类里是加分项。
5. **零故障面**：没有模型加载失败、没有显卡驱动问题、没有首发当天 1 万人同时加载 1.1 GB 的退款。

## 三、什么时候方案 ② 才是对的

诚实地说，有三种情况：

1. **决策真的依赖长尾上下文**：比如“这个殖民者记得 12 天前你处决了他的兄弟”，这种组合无法离散化——但它更适合放在**记忆/情绪系统**里（加权到表上），而不是让模型每次重读全文。
2. **你要 AI 开口解释自己**：需要自然语言 → 那是“表达层”，可以单独用一个小模型（或预生成台词），不影响决策层。
3. **表明显太粗**：试玩后发现玩家能看出“它每次都这样”，且加维度也救不回来。

注意第 3 条是**可测量的**，不是拍脑袋。

## 四、怎么验证你的直觉对不对（重要）

在 M1 就埋点：每次领袖决策时，记录它落在哪个格子（特征向量哈希）。跑 50 小时真实对局后统计：

- **覆盖率** = 出现过的格子数 / 总格子数。如果 95% 的决策落在 5% 的格子里 → 表完全够用，甚至只需要手写那 5%。
- **表外比例** = 落在定义范围外的状态占比。> 5% 说明维度选漏了，加维度比换模型便宜。
- **重复率** = 同一格子的连续决策是否总是一样 → 决定是否要在格内加随机/连续修正。

这套统计同时告诉你：**要不要升级到方案 ②，以及只给哪一部分格子升级。**

## 五、我的建议（具体做法）

1. **v1 走表**：5–6 维、3–5 档、6 个意图；Jev 生成初稿（$1 级成本），你手工修正关键格。
2. **表 + 连续修正**：表给意图，效用函数给“具体打谁、打多狠”，避免粗粒度导致的机械感。
3. **保留模型接口**：决策层抽象成 `decide(features) -> intent`，v1 实现是查表，将来换成小模型只改一个函数。
4. **不要把“训练小模型”放进 v1 的路径**：它是优化项，不是前置项。

**一句话：把 Jev 当成“资深的关卡设计师”，让它把几千个格子填一遍；然后把结果编译成数据。这比在玩家机器上再跑一个更差的模型，便宜、稳、且更好调。**

## 六、能不能给“所有单位”用

要先把两件事分开：**Jev 填表是离线的，运行时只有查表。**

| | 谁在做 | 延迟 | 成本 | 频率上限 |
|---|---|---|---|---|
| 填表 | Jev（云端） | 0.3–1 s/次 | $0.0001/次 | 一次性，离线 |
| 查表 | 游戏内 | **微秒级** | **0** | 无上限 |

所以“给所有单位查表”在性能和成本上完全没问题：60 个单位 × 每秒 2 次 = 120 次查找/秒，哈希命中，纳秒到微秒级；10 万格 × 6 选项 ≈ 600 KB 内存。

**真正限制它的不是速度，是另外三件事：**

1. **维度爆炸**。领袖只要 5–6 维（3k 格）；单位要的是“饥饿 × 疲劳 × 心情 × 技能 × 最近的活 × 局部威胁 × 装备”，轻松上 10^5–10^6 格。可以，但要接受“表变大、标注变贵”（仍然只有几十美元级）。
2. **蜂群感**。如果所有单位查同一张表，相同状态下它们会做出**完全相同**的决定，玩家一眼看出是脚本。必须加个体差异：性格参数（勇气/懒散/洁癖）、随机 tie-break、承诺机制（决定后锁 5–10 秒不改变）。注意：**每个单位看到的局部状态本来就不同**（视野、距离、手头的活），这本身就会产生分化——前提是你把“局部状态”而不是“全局状态”喂给表。
3. **抖动**。表是确定性的，状态在边界上抖一下就会来回改主意。用滞回（hysteresis）：当前意图获得 +15% 权重，除非差距很大否则不切换。

**如果一定要让 Jev 实时服务所有单位**：20 个单位 × 每秒 0.5 次 = 3.6 万次/小时 ≈ **$3.6/小时/玩家**，是这款游戏单份净收入的 1.8 倍/小时。不可行。

**建议的分层：**

| 层 | 对象 | 机制 |
|---|---|---|
| 宏观 | 3–5 个领袖 | Jev 填的表（3k 格），每 30–60 秒 |
| 中观 | 队长/工头（每 8–10 人一个） | 更小的表（局部目标分配），每 5–10 秒 |
| 微观 | 每个单位 | 效用函数 + 上层的意图约束（不查大表） |

这样“所有单位都有决策”成立，但只有关键节点消耗大表——和 Cicero“规划器管大局、执行器管细节”的分工一致。
