# 2D 美术方案：游戏开发经营类（单人 + AI 辅助）

**日期**：2026-11-04 ｜ **状态**：方案（未开工）

---

## 0. 一句话方案

**扁平矢量 UI + 粗描边双色图标 + 剪影卡面 + 等距扁平场景**，全部锁在一套 12 色色板、一个描边宽度、一个圆角半径里；一致性靠脚本检查，不靠眼力。

---

## 1. 结论先行：为什么不选另外三条路

| 风格 | 为什么不做 | 唯一适用条件 |
|---|---|---|
| **像素风**（GDT、City Game Studio） | AI 出像素图一致性差（抖动、描边、色数都不稳）；UI 排版在像素尺度上极难；分辨率受限，中文字体几乎无法落地 | 你愿意手工逐像素修 |
| **全插画**（Cultist Simulator、Griftlands） | 卡面全立绘，一致性和迭代成本最高；脸和手正是 AI 最差的部分 | 你有稳定的画师 |
| **3D 渲染转 2D** | 上一轮已否决（见 game-concept 待定 2） | 空间成为玩法时 |

**扁平矢量的优势**：可参数化（大部分 UI 元素根本不需要图）、可脚本量化、AI 出图后处理简单、中文字体天然适配、缩放到任何分辨率都清晰。

---

## 2. 画面构成：哪些要图，哪些不要

关键发现：**扁平 UI 在 Godot 里用 `StyleBoxFlat` 参数化，大部分"面板/按钮/边框"不需要任何图片资产。**

| 层 | 占比 | 是否要图 | 数量 |
|---|---|---|---|
| 面板、按钮、输入框、tab、modal | ~60% 屏幕 | **不要**（`StyleBoxFlat`：颜色 + 圆角 + 描边参数化） | 0 |
| 图标（资源、品类、属性、状态） | ~15% | 要 | **50–60 个** |
| 卡面（制作人） | ~10% | 要 | **12–20 张 + 3–4 种卡框** |
| 事件插图 | ~5% | 要（可与卡面共用风格） | **8–12 张** |
| 等距工作室背景 | ~5% | 要（1 底图 + 3 家具层 + ~25 件道具） | **约 29 件** |
| Steam 商店素材 | — | 要 | **10 张必需 + 2–3 张可选** |
| 品牌 Logo | — | 要 | **1 套（横版 / 竖版 / 方形）** |
| 字体 | — | 要（开源） | 2–3 款 |
| 动效（数字滚动、卡牌翻面、面板滑入） | — | **不要**（Tween 代码） | 0 |

**合计约 105–135 张图**（含商店素材），其余全是代码画的。

## 3. 四条一次性决定（半小时能写完，之后不许改）

这是"不是 UI 设计师也能做出像样 UI"的核心。全部写进 `docs/art-bible.md`。

### 3.1 调色板关系（不是调色板本身）

**规则：UI 用世界的色相、但压到低饱和 + 更暗的明度带。**

- **世界调色板（12 色）**：4 个主色相 × 3 档明度。用于图标、插画、场景。
- **UI 调色板**：从世界调色板取同样的色相，把饱和度压到 20–35%，明度压到 12–22%。
- 理由：UI 永远压在世界之上，必须"同属一个世界但退后"。这条规则一次解决"金币图标在沙漠背景上看不见"这类问题。

写死数值（可直接抄）：

```
面板底      #14171E @ 25% 透明度
面板描边    #D2DCF5 @ 85% 透明度
正文        #F5F5F5
次要文字    #D2DCF5
强调色      #(世界调色板主色相, 饱和度 70%, 明度 60%)
危险/负值   #(世界调色板红向色相, 同上)
```

### 3.2 形状语言

- **一个圆角半径**：面板 10px、按钮 8px、图标底板 6px（三档，不许出现第四档）。
- **一个描边宽度**：所有图标 **2px @ 96×96 源图**；UI 元素 1px。
- **一个内缩约定**：内容永远距离边框 `10px 上下 / 14px 左右`（沿用 SurvivorCore 的实测值）。

### 3.3 权重阶梯（三级，且不能只靠颜色区分）

| 级别 | 用途 | 区分手段（必须≥2 种） |
|---|---|---|
| 主 | 主操作、当前选中 | 填充 + 亮度 + 字重 |
| 次 | 常规操作 | 描边 + 常规字重 |
| 环境 | 说明、单位、时间戳 | 无边框 + 降饱和 + 小一号 |

只靠颜色区分，会在色弱或未校准的显示器上失效。

### 3.4 状态集（每个交互元件一次定全）

`normal / hover / pressed / disabled / focus / selected` 六态。**先定全再画**，否则后面每加一个界面都要补一次。

## 4. AI 出图管线

### 4.1 三层约束（一致性来自生成之前的约束，不是来自提示词技巧）

1. **风格块（style block）**：写死在文本文件里，逐字粘贴到每一次生成，不按资产改。
   ```
   2D game asset, flat vector style, 2px dark outline, flat shading,
   no gradients, max 12 colors, limited muted palette, soft top-left light,
   2:1 isometric camera (props only), centered, transparent background,
   readable silhouette at 96px, no text, no UI frame
   ```
2. **参考图（reference）**：先用 5 个"锚点资产"定死风格（一个图标、一张卡面、一张场景、一个面板、一张胶囊局部），之后每次生成都带锚点图做 style reference。
3. **统一清理（cleanup pass）**：**所有**输出走同一条后处理——去背、缩到目标尺寸、量化到 12 色、按描边规则加/修 2px 描边、统一安全边距。

> LoRA 只在"还剩几百张图要做"时才划算。70–100 张的规模，风格块 + 锚点 + 清理三项就够，省下的时间是纯赚。

### 4.2 五图标试点（先做这个，不要先做 60 个）

1. 选 5 个最典型的图标（一个资源、一个品类、一个属性、一个状态、一个卡牌类型）。
2. **同一画布契约**：96×96、中心 80% 安全区、透明底、单主体、无文字。
3. 在同一背景（浅/深/真实 UI 底色）**按游戏内实际尺寸**并排对比。
4. **四尺度可读性关卡**：分别在 128 / 64 / 48 / 32 下打分（轮廓、主体分离、安全边距、家族一致性）。
5. 只修离群的那一两个，再扩到全套。
6. **不通过就回到 3.2/3.3 改规则，不要修单张图**——修单张图是在掩盖规则错误。

### 4.3 卡面：不要画全身立绘

**卡面 = 剪影/半身 + 标志性道具 + 强排版。**

- 理由一：AI 画脸和手最不稳，剪影和道具最稳。
- 理由二：制作人卡的辨识度本来就应该来自"符号"（红帽子、圆眼镜、大胡子、耳机），而不是五官。
- 理由三：剪影 + 道具的一致性靠形状就能保证，不靠风格迁移。

**排版比插画重要**：卡面 40% 面积给标题与效果文本，25% 给剪影，其余留白。文字排版用代码做，AI 只出剪影。

### 4.4 等距场景：一张图分层复用

- 出 1 张"主场景"，用图层拆分（地面/墙体/家具/前景），Godot 里按工作室等级换家具层。
- 好处：3 个工作室等级 = 1 底图 + 3 套家具层，而不是 3 张完整场景。
- 相机固定 2:1 等距，不许旋转——老玩家要的是"一眼认出"。

## 5. 一致性靠代码，不靠眼力

这是对美术新手最重要的一条。写四个脚本（Node 或 Python，各几十行）：

| 脚本 | 检查什么 | 失败时 |
|---|---|---|
| `check-palette.mjs` | 每张图的唯一颜色数 ≤ 12，且都在色板内（容差 ΔE < 3） | 报出越界色与占比 |
| `check-outline.mjs` | 图标描边宽度 = 2px（沿 alpha 边界测） | 报出厚度分布 |
| `check-canvas.mjs` | 96×96、主体占 70–85%、安全区留空 | 报出实际占比 |
| `check-set.mjs` | 同一批图标并排生成"家族对照图"（4 尺度） | 输出对比图供人判断 |

前三个是**机器可判**的，第四个留给人。这样你每天的工作从"看 60 张图判断好坏"变成"看报告里的 3 个红点"。

## 6. Godot 落地

### 6.1 用 `StyleBoxFlat`，不要用图片

```gdscript
var sb := StyleBoxFlat.new()
sb.bg_color = Color("#14171E", 0.25)
sb.border_color = Color("#D2DCF5", 0.15)
sb.set_border_width_all(1)
sb.set_corner_radius_all(10)
sb.content_margin_left = 14
sb.content_margin_right = 14
sb.content_margin_top = 10
sb.content_margin_bottom = 10
```

**收益**：面板/按钮/tab/modal 全部零图片资产，改风格只改一个 `Theme` 资源，缩放不糊。

### 6.2 Theme 资源统一

- 一个 `theme.tres`，声明所有 `font_size` / `font_color` / `StyleBox*` / `constant`。
- 界面上**禁止**内联颜色和字号，全部走 theme 变体（`theme_type_variation`）。
- 这三档字重（主/次/环境）对应三个 theme variation，而不是三处手写字号。

### 6.3 分辨率与字体

- 基准 **1920×1080**，拉伸模式 `canvas_items`，宽高比 `expand`。
- UI 全部用 `Control` + `Container`（`VBoxContainer`/`GridContainer`），禁止绝对定位像素坐标。
- 中文：**Noto Sans SC**（OFL，动态字体，`multichannel_signed_distance_field = true` 让任意字号都清晰）。
- 数字：**等宽字体**（JetBrains Mono / Roboto Mono），否则数值跳动时整行抖动——经营类游戏这点很致命。

### 6.4 图标与图集

- 源图 **96×96**，运行时按需 48/64 显示，导出时打成一张 atlas（`AtlasTexture`），减少 draw call。
- 不要为每个尺寸单独出图；用 mipmap + 线性过滤，或干脆只出 96 一张。

## 7. 工时估算

| 阶段 | 内容 | 工时 |
|---|---|---|
| 风格圣经 | 第 3 节四条决定 + 写进 `art-bible.md` | 4 小时 |
| 锚点资产 | 5 个图标 + 1 卡面 + 1 场景 + 1 胶囊局部 | 1 天 |
| 检查脚本 | 4 个脚本 + 跑通 | 1 天 |
| 图标全套 | 40–60 个（含返工） | 3–5 天 |
| 卡面 | 12–20 张 | 3–4 天 |
| 事件插图 | 8–12 张 | 2 天 |
| 等距场景 | 1 底图 + 3 套家具层 | 2–3 天 |
| 胶囊与商店素材 | 主视觉 + 胶囊 + 截图美化 + GIF | 3–4 天 |
| **合计** | | **约 3 周** |

其中**胶囊与商店素材占近 1/4**——这不是浪费：它直接决定"有没有人点进来"，而我们自己的数据显示 85% 的游戏零评测。

## 7.5 Steam 商店素材：精确尺寸（2024-08 后的现行标准）

**注意：网上一大批教程仍在引用已废止的旧尺寸。** 460×215 / 231×87 / 374×448 都已不再接受。

| 素材 | 尺寸 | 必需 | 要点 |
|---|---|---|---|
| Header Capsule | **920×430** | 是 | Logo 必须清晰可读 |
| Small Capsule | **462×174** | 是 | 极宽（2.65:1），构图要单独考虑 |
| Main Capsule | **1232×706** | 是 | 商店首页轮播 |
| Vertical Capsule | **748×896** | 是 | **竖版（0.83:1）**，必须单独构图 |
| Screenshots | ≥1920×1080，16:9 | 是 | 5–8 张 |
| Library Capsule | **600×900** | 是 | 玩家库网格，竖版 |
| Library Header | **920×430** | 是 | 可与 Header Capsule 同图 |
| Library Hero | **3840×1240** | 是 | **不含文字**（Logo 单独叠加）；只有中心 860×380 在所有窗口尺寸下保证可见 |
| Library Logo | 1280 宽 / 720 高，PNG | 是 | 透明底，只放 Logo |
| App Icon | 184×184 (.jpg) | 是 | 小图必须认得出 |
| Shortcut Icon | 256×256 (.ico/.png) | 是 | 提供 png 会自动生成 ico |
| Page Background | 1438×810 | 否 | Steam 会大幅压暗+模糊边缘，内容必须居中 |
| Event Cover | 800×450 | 否 | 用于更新公告 |
| Event Header | 1920×622 | 否 | 可选 |

**生产上的关键推论**：这些尺寸的宽高比从 **2.65:1（极宽）到 0.83:1（竖版）**，跨度极大——**不可能用一张图裁切到底**。实际做法是：**1 张主视觉定调 + 2 个构图（宽版 / 竖版）+ 1 张超宽场景（Hero）**，其余靠裁切与排版。Library Hero 不含文字这一条最容易返工。

## 8. 验收标准

一份美术资产"做完"的定义：

1. 通过 `check-palette` / `check-outline` / `check-canvas` 三个脚本；
2. 在 128/64/48/32 四个尺度下都能认出主体；
3. 与同批资产并排看，不出现"这一个明显不一样"；
4. **已经在引擎里按真实 UI 背景看过**——不在图片查看器里验收。
