## 为什么是这些版本

### opencode `2.2.5`

- `2.2.x` 修的是我们**每天在用**的路径（见 [2.2.0 起的 release notes](https://github.com/sst/opencode/releases/tag/v2.2.0)）：长工具调用/未变更请求的内存回收、加载会话 diff 不再读取全部消息、限流不再被误判成上下文溢出、compaction 的 prompt 按模型窗口封顶（2.2.5 新增 `compaction.buffer` 支持百分比，我们不设，保持 MC 独占窗口）。
- 用 `is:issue 2.2.5` 扫过 open issue：命中的是 Windows/Desktop/ACP/TUI/Console 与我们不用的 integration 路径。两条记录在案但与本次无关：**#61318**（主/子 agent 用同一模型并行时互相挤掉 prompt cache——本环境很少并行同模型子会话）、**#60997**（2.2.5 升级后第三方 integration 不可选——已 closed，且我们不用）。
- 本版本对本地插件的影响：`@opencode/plugin` 2.2 把根入口改成 Promise API、Effect API 移到 `@opencode/plugin/effect`，但根仍 `export * as Plugin`，`plugins/sysinfo`、`plugins/session-search` 的 `import { Plugin }` + `ctx.tool.transform` 不用改（升级后按 §6 实测两个工具可用即验证）。

### OpenChamber `2.6.0`

- **兼容门禁**：`2.6.0` 的 `server/lib/opencode/compatibility.js` 里 `MINIMUM_OPENCODE_VERSION = '2.2.4'`（包内实测），与本 BD 的 opencode 2.2.5 满足。`2.5.3` 那条线是 `2.2.0`。
- **r0 为什么先是 2.5.3**：按新规则扫 issue 时 2.6.0 有两个落在我们路径上的未修回归，故取次新的干净版本。r1 由 owner 决定直接跟 latest，理由记录在 `BD-INDEX.md`（BD 可回退，且 2.6.0 带来侧栏 sections、chat 内表格/图表/表单、prompt 历史等日常可见改进）。
- **已知未修回归（已接受）**：
  - [#6131](https://github.com/openchamber/openchamber/issues/6131) agent 用 `question` 提问时没有提交/关闭按钮。根因已定位（新 UI-block 表单只把 `Button` 节点算作 decision，纯字段表单发不出去），上游标记 `fix-ready` 但尚未发版。**实测与规避**：用 `openchamber_render` + `awaitAnswer` 的页面（带 `Button`）不受影响；受影响的是纯字段表单。若 `question` 真的答不了，就改用页面式提问。
  - [#6084](https://github.com/openchamber/openchamber/issues/6084) 主进程按项目以约 3 次/秒 spawn `git`（报告写明 2.5.3 正常）。本容器 pids 上限 1000，需盯 `pids.current`。
  - [#6108](https://github.com/openchamber/openchamber/issues/6108) 页面 `awaitAnswer` 期间若有 dispatched session 的结果返回，页面会失焦、会话看似卡住。规避：等页面答复后再等子会话结果。
- **代价**：2.5.2 起侧栏 Tree/List 切换被上游故意移除（#5669），升 opencode 2.2 就必须接受"works"式侧栏。2.6.0 的自定义 sections（可按项目分组、可按 `kind=worktree` 过滤）是替代方案；缓解手段还有钉住 worktree、按分支命名 worktree。
- **r2：换成 fork 构建**。上游唯一的可用替代（#5669 回退 Tree 视图）没有进展，而 works 视图把项目下的 worktree 与会话平铺混排。fork 加的是 `sidebarGroupRootWorktrees`（默认开）：打开时项目先列根会话，每个 worktree 作为可折叠分组排在后面，折叠/展开、Show more、搜索、In work、归档都沿用上游逻辑；关闭即上游行为。安装面上它仍是 2.6.0 的代码，所以版本门禁（`MINIMUM_OPENCODE_VERSION = 2.2.4`）和启动契约都不变；npm 的 `@openchamber/web@2.6.0` 没有补丁，镜像改为从 tarball 安装并在构建期断言 `dist` 里含 `groupRootWorktrees`。重新生成 tarball 的步骤见仓库 `README.md`。
- 启动契约核对（`2.6.0` 包内实测）：`--host`、`--ui-password`、`--foreground`、`OPENCHAMBER_DATA_DIR`、`OPENCODE_PORT`、`OPENCHAMBER_OPENCODE_HOSTNAME`、`POST /api/openchamber/update-install` 全部仍在，`entrypoint.sh` 的启动参数不用改。

### magic-context `0.49.34`

- 相对 0.49.21 拿到的（[release 列表](https://github.com/cortexkit/magic-context/releases)）：`0.49.24` 工具定义改动导致的单次 cache 重建、`0.49.25` 工具定义 token 只增不减造成的**假"满上下文"→ 紧急清理**、`0.49.29` **OpenCode 2.2.0 的 instruction 更新行**（不升级会在 summarizer 里被当成用户发言）+ 侧栏 total tokens 归零修复、`0.49.30`/`0.49.32` 侧栏轮询与每 pass 的主线程读取、`0.49.33` 工具列表变化导致的两次全量 cache 写入。
- **为什么不是 0.49.35**：[#838](https://github.com/cortexkit/magic-context/issues/838) —— 新的 host fold 会给**没有历史（没有 historian）的子会话**写一个内容为 `<session-history></session-history>` 的空压缩摘要，OpenCode 2.2 之后每次新回合都被 `Schema validation failed … Compaction requires either encrypted content or a summary` 拒绝，会话永久不可继续。触发条件（子会话存储行 > `MC_OC2_HOST_FOLD_ROWS`(1000) 且 `cache_ttl` 有限）在我们这里是可达的：`magic-context.jsonc` 明确钉了 `cache_ttl.default = 5m`，且我们常用子会话。同版本还有 [#834](https://github.com/cortexkit/magic-context/issues/834)（每个 pass 复制全量历史 2–3 次）未修。
- 0.49.34 是**引入 host fold 之前**的最后一个版本，因此代价是放弃长会话提速（25k 消息会话实测 1.3–2.0 s → 0.33–0.49 s/step）；这笔账记在 `BD-INDEX.md` 的 Hold 里，#838 修好后立刻补上。
- 配置兼容性：`magic-context.jsonc` 的键集合在 `v0.49.21` 与 `v0.49.34` 的 `assets/magic-context.schema.json` 之间**无增无删**，配置不需要改；0.49.22–0.49.34 的 release notes 均写明 "No database migration is needed"，不会触发 `fail_closed_blocking`。

## 关键捆绑细节

- **OpenChamber 与 opencode 必须成对**：`2.6.0` 要 `opencode ≥ 2.2.4`（包内 `MINIMUM_OPENCODE_VERSION`），本 BD 的 2.2.5 满足；`2.5.3` 那条线只要求 `≥2.2.0`。单独升 OpenChamber 会落进"UI 能开、发消息无响应"。
- **opencode 版本真正生效的是 Dockerfile 那行**：`install-tools.sh` 只在二进制缺失时才装，两处必须同 commit 改；Dockerfile 的构建期断言已同步为 `2.2.5` / `2.5.3`。
- **magic-context 写死精确版本**，`entrypoint.sh` 启动时删掉所有**非当前 spec** 的插件缓存；`MC_PLUGIN_CACHE_SPEC` 已改为 `0.49.34`。
- **`compaction` 两个开关分属两个文件**（`opencode.jsonc` 的 `compaction.auto: false` + `magic-context.jsonc` 的 `compaction.enabled: true`），本次都不动。注意 OpenChamber 2.6.0 起设置页也暴露了 compaction 选项，升级后要确认它仍是关的。
- **`update: "notify"`** 不变。

## 回滚

改回 [BD-001（r2）](BD-001.md) 的四个版本号并重新部署即可。只想退 OpenChamber 这一个：r2 起镜像装的是 fork 构建，改用 npm 上游包要改 `Dockerfile` 的安装行为（把 `COPY` 的 tarball 换回 `npm i -g "@openchamber/web@<v>"`；`scripts/install-tools.sh` 的 `OPENCHAMBER_VERSION` 只是 tarball 缺失时的兜底），opencode 2.2.5 仍满足 2.5.3/2.6.0 的 `≥2.2.0` 与 `≥2.2.4`；插件回滚只需改 `opencode.jsonc` 的 spec，`entrypoint.sh` 会自动清掉不匹配的缓存。会话库：0.49.29 起 magic-context 明确支持 OpenCode 2.2，说明 `expected v2` 的代际检查没变，两边也都不要求迁移，回滚不需要动数据库（升级后按 §6 用 `npx @cortexkit/magic-context@latest doctor --harness opencode` 复核一次）。
